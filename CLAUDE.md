# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Resumen del proyecto

Portfolio fotográfico elegante y minimalista. Monorepo con dos paquetes independientes:

- `backend/` — API sencilla en Node.js + Express + TypeScript (ESM) que sirve el catálogo de álbumes/fotos desde una base de datos SQLite y las imágenes como archivos estáticos.
- `frontend/` — Aplicación Angular (standalone components, sin librería de UI) que consume esa API y presenta las fotos.

El catálogo (fotógrafos, portfolios, álbumes, fotos, tags) vive en una base de datos **SQLite** (`backend/datos/BD/portfolio.db`, acceso con `better-sqlite3`). Las imágenes siguen siendo ficheros en `backend/datos/fotos`. **Toda la carpeta `backend/datos` (BD, fotos y logos) está en `.gitignore`**: el repositorio refleja siempre una base de datos vacía y los datos viven solo en cada instalación (en el NAS, en el volumen montado). Un clon nuevo arranca con la BD vacía (se crea sola).

## Comandos

### Backend (`backend/`)

```
npm install         # instalar dependencias
npm run dev          # servidor de desarrollo con recarga (tsx watch), puerto 3000
npm test             # tests (node:test + tsx): reglas de negocio y respuesta de errores de la API
npm run typecheck    # tsc --noEmit
npm run db:importar -- <fichero.json>   # carga masiva de un catálogo en JSON si la BD está vacía (--reemplazar para sustituirlo)
npm run fotografo:renombrar -- <fotógrafo> "<nuevo nombreInformal>"   # cambia el nombreInformal y renombra su carpeta
npm run portfolio:renombrar -- <fotógrafo> <portfolio> "<nuevo nombre>"          # cambia el nombre del portfolio y renombra su carpeta
npm run album:renombrar -- <fotógrafo> <portfolio> <álbum> "<nuevo nombre>"      # ídem para un álbum
npm run build         # compila a dist/ (tsc)
npm start             # ejecuta dist/index.js (requiere build previo)
```

### Frontend (`frontend/`)

```
npm install                     # instalar dependencias
npm start                        # ng serve, puerto 4200
npm run build                    # build de producción
npx ng test --watch=false        # ejecuta toda la suite (Vitest) una vez
npx ng test --watch=false -- <patrón>   # ejecutar un subconjunto de tests por nombre/archivo
```

El frontend espera la API en `http://localhost:3000` (constante `API_BASE_URL` en `frontend/src/app/core/config/api.config.ts`). Para probar la app completa hay que tener backend y frontend corriendo a la vez.

## Arquitectura

### Modelo de datos

Jerarquía: **fotógrafo → portfolios → álbumes → fotos**. Fotógrafo: `nombreInformal` (obligatorio; p. ej. "Santi Estévez", texto con el que se dibuja su logo), `nombreInformalNormalizado`, `nombre`, `primerApellido` (obligatorio), `segundoApellido` y `email` opcionales, `descripcion`. **`nombreInformalNormalizado`** es `normalizarNombre(nombreInformal)` (`santi-estevez`), es único y es a la vez el identificador del fotógrafo en las URL, el nombre de su logo (`datos/logos/santi-estevez.svg`) y **el nombre de su carpeta** (`datos/fotos/santi-estevez/`). Debe coincidir SIEMPRE con la carpeta: lo calcula la aplicación (alta, importación y `cambiarNombreInformal()` en `backend/src/services/fotografo.service.ts`) y nunca se edita a mano. Cambiar el `nombreInformal` se hace con `cambiarNombreInformal()` (o `npm run fotografo:renombrar`): actualiza la BD y renombra la carpeta en la misma transacción (si el renombrado falla, la BD no cambia), rechaza nombres que coincidan con otro fotógrafo o con una carpeta existente, y borra el logo anterior para que se regenere. No hay endpoint para esto (aún no hay login). Al arrancar, el backend avisa en consola si a algún fotógrafo le falta su carpeta. El fotógrafo tiene además un `usuario` interno (inicial del nombre + 3 primeras letras del primer apellido, sin tildes: `sest`; con sufijo numérico si se repite; `backend/src/utils/usuario.ts`) que **no se muestra ni sale en la API** y hoy no se usa para nada más (reservado para el login). Portfolio y álbum: `nombre`, `descripcion` opcional y **`nombreNormalizado`** = `normalizarNombre(nombre)` (único dentro de su padre), que funciona igual que el `nombreInformalNormalizado` del fotógrafo: es su identificador en las URL (la API lo devuelve) y **el nombre de su carpeta**. Lo calcula la aplicación al guardar el nombre y nunca se edita a mano. Cambiar el nombre se hace con `renombrarPortfolio()` / `renombrarAlbum()` (`backend/src/services/portfolio.service.ts` y `album.service.ts`, o `npm run portfolio:renombrar` / `album:renombrar`) o con `editarPortfolio()` / `editarAlbum()` (endpoints `PUT`): recalculan el `nombreNormalizado` y, si cambia, renombran la carpeta en la misma transacción que la BD; rechazan nombres que coincidan con otro portfolio/álbum del mismo padre o con una carpeta existente. Crear un portfolio/álbum crea su carpeta y eliminarlo la borra, siempre con el `nombreNormalizado` como nombre. La portada de un portfolio es la del primer álbum. Un álbum tiene `tags` (cuelgan del álbum, no de la foto) y fotos ordenadas. Las fotos están en `datos/fotos/<nombreInformalNormalizado>/<nombreNormalizado portfolio>/<nombreNormalizado álbum>/<nombreFichero>` y se sirven en `/photos/...` con esa misma ruta, que coincide con la de la web. Los ids y el `usuario` son internos: no aparecen ni en la API ni en las URL. **En las URL y en las carpetas nunca hay mayúsculas, tildes ni espacios.** **`normalizarNombre()`** (`backend/src/utils/normalizar-nombre.ts`) es el único helper que normaliza nombres (fotógrafos, portfolios y álbumes): quita los espacios de los extremos, pasa a minúsculas, "ñ" -> "ny", quita tildes y cambia cada grupo de espacios intermedios por un guion (`/lucia-martin/proyectos-personales/editorial`, "Montaña" -> `montanya`, "Irene Castaño" -> `irene-castanyo`). Está duplicada a propósito en el frontend (`core/utils/normalizar-nombre.ts`, solo para el guard de URL canónica) y debe mantenerse idéntica. Un nombre cuya forma normalizada no sirve como carpeta (contiene `/` o `\`, o empieza por `.`) se rechaza con la regla `NOMBRE_NO_VALIDO`. El backend la registra como función SQL (`db.function` en `db/conexion.ts`, porque `lower()` de SQLite solo convierte ASCII) para normalizar el segmento que llega en la URL antes de compararlo con la columna normalizada, así que la API acepta cualquier variante. En la web, el guard `core/guards/url-canonica.ts` (en las rutas con parámetros) redirige cualquier URL escrita con mayúsculas, tildes o espacios a su forma canónica (`/Santi Estévez` -> `/santi-estevez`, `/marta-vidal/encargos/montaña` -> `.../montanya`). "Ciudad de noche", "Ciudad-de noche" o "ciudad de noche" darían la misma URL y la misma carpeta: las reglas de negocio lo rechazan y el índice único sobre `nombreNormalizado` es la última defensa. Tampoco se controlan las mayúsculas en `nombreFichero` (las URL de `/photos/` usan el nombre real del fichero). Si `normalizarNombre()` cambia, habría que recalcular las columnas normalizadas y renombrar las carpetas (con una migración, como la de la versión 9). La API usa el mismo vocabulario que la BD (`nombre`, `descripcion`, `fotos`, `nombreFichero`, `titulo`, `orden`, `ancho`, `alto`…); solo los campos calculados siguen en inglés (`coverPhotoUrl`, `photoCount`, `albumCount`, `portfolioCount`, `logoUrl`, `url`).

- Fuente de verdad: la base de datos SQLite `backend/datos/BD/portfolio.db` (ruta configurable con `DB_PATH`; no versionada: `backend/datos/` está en `.gitignore`). Esquema en `backend/src/db/conexion.ts`, notación lowerCamelCase: `fotografos` (PK `idFotografo`, `usuario` único, `nombreInformal`, `nombreInformalNormalizado` único, `nombre`, `primerApellido`, `segundoApellido`, `email` opcional y único sin distinguir mayúsculas, `passwordHash`, `descripcion`), `portfolios` (PK `idPortfolio`, FK `idFotografo`, `nombreNormalizado`, `nombre`, `descripcion`, `orden`; UNIQUE `(idFotografo, nombre)` e índice único `(idFotografo, nombreNormalizado)`), `albumes` (PK `idAlbum`, FK `idPortfolio`, `nombreNormalizado`, `nombre`, `descripcion`, `idFotoPortada` FK a `fotos`, `orden`; UNIQUE `(idPortfolio, nombre)` e índice único `(idPortfolio, nombreNormalizado)`), `fotos` (PK `idFoto`, FK `idAlbum`, `nombreFichero` único por álbum, `titulo`, `orden`, `ancho`, `alto`) y `albumTags` (PK `idAlbum, tag`). Claves foráneas en cascada; los fotógrafos se listan por `idFotografo` (orden de alta). `fotografos`, `portfolios`, `albumes` y `fotos` tienen `fechaCreacion` y `fechaModificacion` (texto ISO 8601 UTC) mantenidas por la BD: DEFAULT y un trigger `<tabla>FechaModificacion` AFTER UPDATE. `passwordHash` guardará solo el hash (aún no hay alta/login; queda NULL) y ni el email, ni el hash, ni el `usuario` salen nunca en la API pública. La versión del esquema va en `PRAGMA user_version` (`VERSION_ESQUEMA`, hoy 9); las versiones < 8 solo existieron en desarrollo y se descartan al abrir (el catálogo queda vacío). Desde la 8 cada cambio de esquema añade una migración en `migrar()` que conserva los datos: la 8 -> 9 (`migrarA9`) convierte `nombreCarpeta` en `nombreNormalizado`, lo recalcula a partir del nombre y renombra las carpetas que no coincidían (si algo falla, deshace la BD y los renombrados). Si no existe, la BD se crea vacía al arrancar. `organizacionFotos.json` ya no existe (estaba desfasado respecto a la BD y las carpetas): solo queda `npm run db:importar -- <fichero.json>` para cargas masivas puntuales (hoy, la única forma de dar de alta fotos en bloque). Ese JSON usa el mismo vocabulario: `OrganizacionFotos[]`, cada elemento `{ fotografo: { nombreInformal, usuario?, nombre, primerApellido, segundoApellido?, email?, descripcion }, portfolios: [{ nombre, descripcion?, albumes: [{ nombre, descripcion?, tags, fotoPortada? (nombreFichero), fotos: [{ nombreFichero, titulo?, orden, ancho?, alto? }] }] }] }` (tipos en `backend/src/types/album.ts`; `usuario` opcional para fijarlo si hay homónimos; la contraseña no se importa). Con `--reemplazar` borra antes todo el catálogo de la BD.
- Archivos de imagen reales: `backend/datos/fotos/<nombreInformalNormalizado>/<nombreNormalizado del portfolio>/<nombreNormalizado del álbum>/<nombreFichero>` — deben coincidir exactamente con lo guardado en la BD, o las imágenes no se resolverán. Al importar un JSON las carpetas ya deben llamarse así (la importación no las crea ni las renombra).
- Logos de fotógrafo: nunca los aporta el usuario ni se anotan en la BD; los genera el backend. `GET /api/fotografos/:fotografo/logo` llama a `asegurarLogo` (`backend/src/services/logo.service.ts`), que sirve `backend/datos/logos/<nombreInformalNormalizado>.svg` (p. ej. `lucia-martin.svg`, `irene-castanyo.svg`) y, si no existe, lo genera con el `nombreInformal` como firma. Al cambiar el `nombreInformal`, `cambiarNombreInformal()` borra el logo anterior y se genera uno nuevo en la siguiente petición. El logo es un SVG tipo firma en letra manuscrita Mrs Saint Delafield con un subrayado de plumilla, con el texto convertido a trazos (un `<img>` no puede cargar fuentes) y tinta `#f2f1ed` para el fondo oscuro. La fuente (OFL) está en `backend/assets/fonts` y se copia a la imagen Docker. La API expone solo `logoUrl`.
- Tipos compartidos conceptualmente (no compartidos por código, ya que son dos paquetes npm separados): `backend/src/types/album.ts` y `frontend/src/app/core/models/album.model.ts`. Si se cambia la forma del JSON hay que actualizar ambos.

### Backend (`backend/src/`)

- `index.ts` — arranque de Express, monta `/api` y sirve `/photos` como estático desde `backend/datos/fotos`.
- `routes/albums.routes.ts` — único router: `GET /api/albums` (todos los álbumes con su `fotografo` (nombreInformal) y `portfolio`, filtro opcional `?tag=`), `GET /api/tags` (tags únicos derivados de todos los álbumes), `GET /api/fotografos` (con `portfolioCount` y `albumCount`), `POST /api/fotografos` (alta: `crearFotografo()` en `services/fotografo.service.ts`; cuerpo `FotografoAlta` con `nombreInformal`, `nombre`, `primerApellido` obligatorios y `segundoApellido`, `email`, `descripcion`, `contrasenya` opcionales; responde 201 con los datos públicos, 400 si el cuerpo está mal formado y 422 si incumple una regla; crea también la carpeta `datos/fotos/<nombreInformalNormalizado>` en la misma transacción y guarda solo el hash scrypt de la contraseña, `utils/contrasenya.ts`), `GET /api/fotografos/:fotografo` (fotógrafo + resúmenes de sus portfolios), `GET /api/fotografos/:fotografo/edicion` (datos editables para el formulario, incluido el email; de la contraseña solo `tieneContrasenya`), `PUT /api/fotografos/:fotografo` (edición: mismo cuerpo que el alta, una contraseña vacía conserva la actual; si cambia el nombre informal renombra la carpeta), `DELETE /api/fotografos/:fotografo` (elimina con portfolios, álbumes, fotos, carpeta y logo; si tiene portfolios exige `?confirmar=true`, si no responde 422 con la regla `FOTOGRAFO_ELIMINAR_CON_PORTFOLIOS`, cuyo mensaje es la pregunta que muestra la web; 204 si se elimina), `GET /api/fotografos/:fotografo/logo`, `GET /api/fotografos/:fotografo/portfolios/:portfolio` (portfolio + resúmenes de sus álbumes, filtro opcional `?tag=`; también es lo que carga el formulario de edición), `POST /api/fotografos/:fotografo/portfolios` (alta: cuerpo `PortfolioAlta` `{ nombre, descripcion? }`; se añade al final de los del fotógrafo y crea su carpeta; 201 con el `PortfolioDetalle`, 400 si el cuerpo está mal formado, 422 si incumple una regla), `PUT /api/fotografos/:fotografo/portfolios/:portfolio` (mismo cuerpo; si cambia el nombre renombra la carpeta; devuelve el portfolio con su nuevo `nombreNormalizado`), `DELETE /api/fotografos/:fotografo/portfolios/:portfolio` (elimina con álbumes, fotos y carpeta; si tiene álbumes exige `?confirmar=true`, si no 422 con la regla `PORTFOLIO_ELIMINAR_CON_ALBUMES`; 204), `GET /api/fotografos/:fotografo/portfolios/:portfolio/albums/:album` (álbum con `portfolio: { nombre, nombreNormalizado }` y `fotos`; también es lo que carga el formulario de edición), `POST /api/fotografos/:fotografo/portfolios/:portfolio/albums` (alta: cuerpo `AlbumAlta` `{ nombre, descripcion?, tags? }`; se añade al final de los del portfolio y crea su carpeta; 201 con el `AlbumDetalle`, 400/422 como en portfolios), `PUT …/albums/:album` (mismo cuerpo, sin tags = ninguno; si cambia el nombre renombra la carpeta) y `DELETE …/albums/:album` (elimina con fotos y carpeta; si tiene fotos exige `?confirmar=true`, si no 422 con la regla `ALBUM_ELIMINAR_CON_FOTOS`; 204); `:fotografo`, `:portfolio` y `:album` son segmentos de URL (ver `normalizarNombre`). Portfolios y álbumes salen siempre con su `nombreNormalizado`, que la web usa para los enlaces. Los datos públicos del fotógrafo son `nombreInformal`, `nombre`, `primerApellido`, `segundoApellido?`, `descripcion` y `logoUrl`.
- `config/rutas.ts` — rutas a `datos/` (configurable con `DATOS_DIR`, p. ej. para tests), fotos, logos y base de datos (`DB_PATH`, por defecto `datos/BD/portfolio.db`). `db/conexion.ts` — abre la BD (WAL, `foreign_keys`) y crea el esquema. `db/importar.ts` — importa un catálogo en JSON en una transacción (lo usan `db:importar` y los tests para preparar datos). `db/catalogo.repository.ts` — todas las consultas (sentencias preparadas); abre la BD al cargarse. `scripts/importar-json.ts` — CLI de importación (`npm run db:importar -- <fichero.json>`; en el contenedor `node dist/scripts/importar-json.js <fichero.json>`). `services/logo.service.ts` — generación y persistencia de logos. `utils/normalizar-nombre.ts` — `normalizarNombre()` y `esNombreNormalizadoValido()`. `utils/carpetas.ts` — `carpetaOcupada()` (sin confundir un cambio solo de mayúsculas con otra carpeta) y `renombrarCarpeta()`. El paquete es ESM (`"type": "module"`, `module`/`moduleResolution: NodeNext`).
- `reglas/` — **reglas de negocio** (ver sección "Reglas de negocio"). `errores.ts` — `RecursoNoEncontrado` (404). `gestionar-errores.ts` — middleware de Express que responde 422 a una regla incumplida y 404 a un recurso inexistente. `services/fotografo.service.ts` — `crearFotografo`, `editarFotografo`, `cambiarNombreInformal` y `eliminarFotografo`: validan las reglas en su operación y mantienen la carpeta del fotógrafo sincronizada con la BD (al eliminar, la carpeta se aparta a `datos/fotos/.papelera-*` dentro de la transacción y se borra después; las carpetas con punto no se sirven en `/photos`). `services/portfolio.service.ts` — `crearPortfolio`, `editarPortfolio`, `eliminarPortfolio` y `renombrarPortfolio`, con el mismo esquema (validar en su operación, BD y carpeta en la misma transacción). `services/album.service.ts` — `crearAlbum`, `editarAlbum` (nombre, descripción y tags), `eliminarAlbum` y `renombrarAlbum`, igual. Al eliminar (fotógrafo, portfolio o álbum) la carpeta se aparta con `apartarCarpeta()` y se borra con `vaciarPapelera()` (`utils/carpetas.ts`). **El mantenimiento de portfolios y álbumes es cosa del fotógrafo propietario, no del administrador**: sus rutas cuelgan del fotógrafo (API) y de `/gestion/:fotografo/…` (web), para que, cuando haya login, baste con comprobar que el usuario es ese fotógrafo.

### Reglas de negocio (`backend/src/reglas/`)

Todo lo que la aplicación no permite ("un fotógrafo no puede tener dos portfolios con el mismo nombre") se gestiona en un único módulo:

- `catalogo.ts` — **único sitio donde se definen las reglas y se redactan sus textos**: `REGLAS` (código -> mensaje, p. ej. `PORTFOLIO_NOMBRE_DUPLICADO: 'Ya existe otro portfolio con el mismo nombre ("{nombre}") para este fotógrafo.'`) y `OPERACIONES` (código -> descripción en infinitivo de lo que se intentaba hacer, p. ej. `CREAR_PORTFOLIO: 'Crear el portfolio "{nombre}" del fotógrafo "{fotografo}"'`). Los `{campo}` se rellenan con los datos al incumplirse.
- `regla-incumplida.ts` — el error `ReglaNegocioIncumplida` (código, datos, mensaje de la regla y, opcionalmente, la operación intentada), `exigir(condición, código, datos)` / `incumplir(código, datos)` para lanzarlo, y `enOperacion(códigoOperación, datos, fn)` que envuelve una acción para que cualquier regla incumplida dentro salga acompañada de lo que se intentaba (se conserva la operación más interna). `toJSON()` es la respuesta de la API y `aTexto()` la salida de consola.
- `validaciones.ts` — `validadorCatalogo(db)`: las comprobaciones que consultan la BD (nombres de portfolio/álbum duplicados comparados en su forma normalizada, nombres que no sirven como carpeta, carpeta de destino ocupada al renombrar, nombre informal/correo/usuario repetidos, fichero repetido en un álbum, foto de portada inexistente, tags repetidos, obligatorios…). Aceptan el id del propio elemento (`excluir`) para las modificaciones. El repositorio exporta `validar` (validador sobre la conexión principal).

Todo lo que escribe en el catálogo debe validar antes de guardar y envolverse en su operación: la importación (`db/importar.ts`: `CREAR_FOTOGRAFO`, `CREAR_PORTFOLIO`, `CREAR_ALBUM`, `ANYADIR_FOTO`) `cambiarNombreInformal()` (`CAMBIAR_NOMBRE_INFORMAL`) y `renombrarPortfolio()` / `renombrarAlbum()` (`RENOMBRAR_PORTFOLIO`, `RENOMBRAR_ALBUM`), `crearPortfolio()` / `editarPortfolio()` / `eliminarPortfolio()` (`CREAR_PORTFOLIO`, `EDITAR_PORTFOLIO`, `ELIMINAR_PORTFOLIO`), `crearAlbum()` / `editarAlbum()` / `eliminarAlbum()` (`CREAR_ALBUM`, `EDITAR_ALBUM`, `ELIMINAR_ALBUM`); cualquier endpoint de escritura futuro, igual. Las restricciones UNIQUE/NOT NULL de la BD se mantienen como última defensa. Para añadir una regla: código y mensaje en `catalogo.ts`, comprobación en `validaciones.ts` (o `exigir` donde toque) y un test en `reglas/reglas.test.ts`.

Una regla incumplida en la API se responde con **422** y este cuerpo: `{ tipo: "reglaNegocioIncumplida", operacion: { codigo, descripcion }, regla: { codigo, mensaje }, message }` (`message` = "No se ha podido <operación>. <regla>"). En los comandos (`db:importar`, `fotografo:renombrar`, `portfolio:renombrar`, `album:renombrar`) se muestra la operación y la regla en consola y no se guarda nada (transacción).

### Frontend (`frontend/src/app/`)

Angular standalone (sin `NgModule`), routing con `loadComponent` (lazy):

- `core/services/album.ts` — `AlbumService` (decorador `@Service()`, la forma moderna de `@Injectable` en esta versión de Angular) con un método por ruta del backend (`getFotografos`, `getFotografo`, `getPortfolio`, `getAlbumDePortfolio`, además de los globales `getAlbums` y `getTags`).
- `core/models/album.model.ts` — interfaces con los mismos nombres que la API (`Fotografo*`, `Portfolio*`, `AlbumResumen`, `AlbumEnCatalogo`, `AlbumDetalle`, `Foto`) y la función `nombreCompleto()`.
- `core/config/api.config.ts` — URL base de la API.
- `features/fotografo-list/` — página raíz (`/`), listado de fotógrafos.
- `features/fotografo-form/` — páginas `/admin/fotografos/nuevo` (enlace "+ Nuevo fotógrafo" en la portada) y `/admin/fotografos/:fotografo/editar` (carga los datos de `/edicion`; contraseña vacía = conservar): formulario reactivo de alta y edición con los campos editables del fotógrafo (nombre informal, nombre, apellidos, correo, descripción, contraseña y su repetición). Valida lo básico en el navegador y muestra el aviso de la regla incumplida (operación intentada + motivo) si el backend responde 422; si va bien navega a la página del nuevo fotógrafo. `nombreInformalNormalizado` y `usuario` no se muestran. La ruta va antes que las de parámetros y el prefijo `admin` (igual que `api`, `gestion` y `photos`) está reservado: ningún fotógrafo puede tener esa dirección (regla `FOTOGRAFO_NOMBRE_INFORMAL_RESERVADO`).
- `features/portfolio-form/` — páginas `/gestion/:fotografo/portfolios/nuevo` (enlace "+ Nuevo portfolio" en la página del fotógrafo) y `/gestion/:fotografo/portfolios/:portfolio/editar`: formulario de nombre y descripción del portfolio, con el mismo aviso de regla incumplida que el del fotógrafo; si va bien navega a la página del portfolio. `gestion` es la zona del fotógrafo propietario (frente a `admin`, la del administrador).
- `features/album-form/` — páginas `/gestion/:fotografo/portfolios/:portfolio/albumes/nuevo` (enlace "+ Nuevo álbum" en la página del portfolio) y `.../albumes/:album/editar`: formulario de nombre, descripción y tags (separados por comas) del álbum, igual que el del portfolio; si va bien navega a la página del álbum.
- `shared/album-acciones/` — botones "Editar" y "Eliminar" de un álbum, en cada tarjeta de la página del portfolio y en la cabecera de la página del álbum. Igual que `portfolio-acciones`, con la regla `ALBUM_ELIMINAR_CON_FOTOS`. Emite `eliminado` (la página del portfolio recarga; la del álbum vuelve al portfolio).
- `shared/portfolio-acciones/` — botones "Editar" y "Eliminar" de un portfolio, en cada tarjeta de la página del fotógrafo y en la cabecera de la página del portfolio. Igual que `fotografo-acciones`: si el portfolio tiene álbumes el backend responde con la regla `PORTFOLIO_ELIMINAR_CON_ALBUMES` y su mensaje se muestra en `shared/confirmacion/`; al aceptar se repite con `?confirmar=true`. Emite `eliminado` (la página del fotógrafo recarga; la del portfolio vuelve al fotógrafo).
- `shared/fotografo-acciones/` — botones "Editar" y "Eliminar" de un fotógrafo, en cada tarjeta de la portada y en la cabecera de su página. Eliminar pide al backend borrar sin confirmar: sin portfolios se elimina sin más; con portfolios el backend responde con la regla `FOTOGRAFO_ELIMINAR_CON_PORTFOLIOS` y su mensaje se muestra en `shared/confirmacion/` (diálogo modal con "Sí, eliminar" / "Cancelar"); al aceptar se repite con `?confirmar=true`. Emite `eliminado` (la portada recarga la lista; la página del fotógrafo vuelve a la portada).
- `features/portfolio-list/` — página `/:fotografo` (segmento del `nombreInformal`), grid de portfolios del fotógrafo; muestra "Volver" solo si se ha llegado desde la portada.
- `features/album-list/` — página `/:fotografo/:portfolio`, grid de álbumes del portfolio, con enlace de vuelta a los portfolios.
- `features/album-detail/` — página `/:fotografo/:portfolio/:album`, grid de fotos del álbum con enlace de vuelta a su portfolio (muestra "Álbum no encontrado" si no existe); obtiene los parámetros vía `ActivatedRoute.paramMap` con `switchMap` + `toSignal`.
- `shared/lightbox/` — visor modal reutilizable (controlado por el padre vía `photos`/`index` como inputs y eventos `closeRequested`/`indexChange`); navegación por teclado (flechas, Escape).

Patrón de datos: los componentes usan `toSignal()` (`@angular/core/rxjs-interop`) sobre los observables de `AlbumService` en lugar de `subscribe()` manual; no hay gestión de estado global (no hace falta con esta escala de app).

### Diseño / estilo

Sistema de diseño propio en SCSS (sin Angular Material ni Tailwind, por decisión explícita): tokens como custom properties en `frontend/src/styles.scss` (paleta oscura neutra para que las fotos destaquen, tipografía serif `Cormorant Garamond` para títulos + `Inter` para UI, cargadas vía Google Fonts en `index.html`). Los estilos de cada componente son locales a su carpeta (`*.scss` junto al componente). La cabecera a todo el ancho de las páginas de portfolio y de álbum (datos a la izquierda, mantenimiento a la derecha y línea separadora difuminada debajo, y bajo ella la franja `cabecera-barra` con "+ Nuevo álbum" o "Gestionar fotos", este último aún sin funcionalidad) está en el parcial `shared/estilos/_cabecera.scss`, que cada página incluye con `@use`.

### Despliegue con Docker (NAS)

`docker-compose.yml` en la raíz levanta dos servicios en la red interna `portfolio`, usando imágenes ya construidas en vez de build local:

- `backend` — imagen `ghcr.io/sestevez5/portoliosfotograficos-backend:latest`. No publica puerto al host; solo es accesible desde `frontend` a través de la red de Docker Compose.
- `frontend` — imagen `ghcr.io/sestevez5/portoliosfotograficos-frontend:latest`. Publica un único puerto al host (`FRONTEND_PORT`, por defecto 8080).

Las imágenes se construyen y publican automáticamente en GitHub Container Registry (GHCR) mediante `.github/workflows/docker-publish.yml` en cada push a `main` (tags `:latest` y `:<sha>`). Por eso el NAS **no necesita el código fuente**: solo `docker-compose.yml`, `.env` y la carpeta `datos/` (ver más abajo). Si el paquete de GHCR está en privado, hay que hacer `docker login ghcr.io` una vez en el NAS con un token con permiso `read:packages` antes de poder hacer `pull` (o marcar el paquete como público desde la configuración de GitHub).

`docker-compose.override.yml` (no se copia al NAS) añade `build: context: ...` a ambos servicios y Docker Compose lo aplica automáticamente cuando está presente junto a `docker-compose.yml` — así en local, con el repo completo, `docker compose build`/`up` siguen construyendo las imágenes desde los Dockerfiles en vez de tirar de GHCR. Los Dockerfiles (`backend/Dockerfile`, `frontend/Dockerfile`) son multi-stage: el backend hace `npm run build` + `npm ci --omit=dev` + `node dist/index.js`; el frontend hace `ng build` y sirve `dist/frontend/browser` con nginx.

`frontend/nginx.conf` hace de proxy inverso: sirve los estáticos de Angular y reenvía `/api/` y `/photos/` al servicio `backend:3000`, de forma que el navegador solo ve un origen. Por eso en build de producción `API_BASE_URL` debe ser `''` (ruta relativa) en vez de `http://localhost:3000`: `angular.json` usa `fileReplacements` en la configuración `production` para sustituir `api.config.ts` por `api.config.prod.ts` automáticamente en cualquier `ng build` (o `npm run build`) sin flags adicionales. En desarrollo (`ng serve`) se sigue usando `api.config.ts` tal cual.

La carpeta `backend/datos` (fotos, logos y `BD/portfolio.db`) se monta como volumen externo, no se hornea en la imagen (`backend/.dockerignore` la excluye) ni se versiona. Debe ser escribible por el contenedor (SQLite y logos). En el primer arranque sin `portfolio.db` el backend la crea vacía; para llevar el catálogo al NAS se copia la carpeta `datos` completa (con el backend parado). `better-sqlite3` es un módulo nativo: el Dockerfile instala sus dependencias en una etapa `deps` con `python3 make g++` por si hay que compilarlo (p. ej. NAS ARM) y copia solo `node_modules` a la imagen final. La ruta real en el host del NAS se configura vía variable de entorno `DATOS_PATH` en un fichero `.env` (no versionado; ver `.env.example`) junto con `FRONTEND_PORT`.

Despliegue típico en el NAS (solo con `docker-compose.yml`, `.env` y `datos/` copiados, sin el resto del repo): `cp .env.example .env` (ajustar rutas), `docker compose pull`, `docker compose up -d`. Para desplegar una versión nueva más adelante: `docker compose pull && docker compose up -d` de nuevo.

## Versionado

Versionado semántico `MAYOR.MENOR.PARCHE` (semver), una única versión para todo el monorepo:

- **MAYOR**: cambios incompatibles (p. ej. cambios en la organización de `datos/` que obligan a migrar los datos del NAS, o rutas de la API que desaparecen).
- **MENOR**: funcionalidad nueva compatible hacia atrás.
- **PARCHE**: correcciones sin cambios de funcionalidad.

Al publicar una versión: actualizar `version` en `backend/package.json` y `frontend/package.json` (`npm version X.Y.Z --no-git-tag-version` en cada paquete, que también actualiza el lockfile), añadir la entrada en `CHANGELOG.md`, hacer commit en `develop`, fusionar en `main` y crear el tag anotado `vX.Y.Z` en `main`. El desarrollo diario va en `develop`; `main` solo recibe versiones.

## Notas para seguir desarrollando

- Las fotos actuales son contenido de prueba generado como placeholders de color — hay que sustituirlas por fotos reales.
- **Desde que existe el alta de fotógrafos, la BD es la única fuente de verdad**: y no está en el repositorio. `db:importar -- <fichero> --reemplazar` borraría el catálogo existente. Hacer copias de `portfolio.db` antes de esas operaciones.
- **El alta, la edición y la eliminación de fotógrafos, portfolios y álbumes (`POST`, `PUT`, `DELETE /api/fotografos…`, `/admin/…`, `/gestion/…`) no tienen autenticación todavía**: cualquiera que llegue a la web puede crear, modificar o **borrar de forma permanente** fotógrafos con todas sus fotos, y `GET …/edicion` expone su email. Antes de publicarla fuera de la red local hay que protegerla (login o, como mínimo, un token de administración o restringir `/admin`, `/gestion` y esos métodos en nginx). Con login, `/admin` sería del administrador y `/gestion/:fotografo` y las escrituras en `/api/fotografos/:fotografo/portfolios…` solo del propio fotógrafo.
- Copias de seguridad: basta con copiar `portfolio.db` con el backend parado (o usar `sqlite3 portfolio.db ".backup copia.db"` en caliente). Con WAL activo existen también `portfolio.db-wal`/`-shm` mientras el backend corre.
- `GET /api/albums` sin filtro devuelve todos los álbumes; con miles de álbumes (probado con 1.000 fotógrafos / 100.000 fotos: ~640 KB, ~40 ms) convendría paginarlo si se empieza a usar desde la interfaz. El resto de rutas responde en pocos ms a esa escala.
- Repositorio git inicializado, con remoto en GitHub (`https://github.com/sestevez5/portoliosfotograficos.git`, rama `main`).
