# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Resumen del proyecto

Portfolio fotográfico elegante y minimalista. Monorepo con dos paquetes independientes:

- `backend/` — API sencilla en Node.js + Express + TypeScript (ESM) que sirve el catálogo de colecciones/fotos desde una base de datos SQLite y las imágenes como archivos estáticos.
- `frontend/` — Aplicación Angular (standalone components, sin librería de UI) que consume esa API y presenta las fotos.

El catálogo (fotógrafos, portfolios, colecciones, fotos, tags) vive en una base de datos **SQLite** (`backend/contenido/datos/BD/portfolio.db`, acceso con `better-sqlite3`). Todo el contenido de la aplicación está en `backend/contenido/`, con dos carpetas hermanas, igual que en el NAS: `datos/` (BD, logos, miniaturas y fotos de perfil) y `fotos/` (las fotos, en AVIF). **`backend/contenido/` está en `.gitignore`**: el repositorio refleja siempre una base de datos vacía y los datos viven solo en cada instalación (en el NAS, en el volumen montado). Un clon nuevo arranca con la BD vacía (se crea sola).

## Comandos

### Backend (`backend/`)

```
npm install         # instalar dependencias
npm run dev          # servidor de desarrollo con recarga (tsx watch), puerto 3000
npm test             # tests (node:test + tsx): reglas de negocio y respuesta de errores de la API
npm run typecheck    # tsc --noEmit
npm run db:importar -- <fichero.json>   # carga masiva de un catálogo en JSON si la BD está vacía (--reemplazar para sustituirlo, --anyadir para añadirlo al actual)
npm run fotografo:renombrar -- <fotógrafo> "<nuevo nombreInformal>"   # cambia el nombreInformal y renombra su carpeta
npm run portfolio:renombrar -- <fotógrafo> <portfolio> "<nuevo nombre>"          # cambia el nombre del portfolio y renombra su carpeta
npm run coleccion:renombrar -- <fotógrafo> <portfolio> <colección> "<nuevo nombre>"      # ídem para una colección
npm run fotos:convertir      # convierte a AVIF las fotos guardadas en su formato original y BORRA las originales
npm run build         # compila a dist/ (tsc)
npm start             # ejecuta dist/index.js (requiere build previo)
```

### Frontend (`frontend/`)

```
npm install                     # instalar dependencias
npm start                        # ng serve, puerto 4200
npm run build                    # build de producción
npx ng test --watch=false        # ejecuta toda la suite (Vitest) una vez
npx ng test --watch=false -- <patrón>   # ejecutar un subconjunto de tests por nombre/archivo
```

El frontend espera la API en `http://localhost:3000` (constante `API_BASE_URL` en `frontend/src/app/core/config/api.config.ts`). Para probar la app completa hay que tener backend y frontend corriendo a la vez.

## Arquitectura

### Modelo de datos

Jerarquía: **fotógrafo → portfolios → colecciones → fotos**. Fotógrafo: `nombreInformal` (obligatorio; p. ej. "Santi Estévez", texto con el que se dibuja su logo), `nombreInformalNormalizado`, `nombre`, `primerApellido` (obligatorio), `segundoApellido` y `email` opcionales, `descripcion`. **`nombreInformalNormalizado`** es `normalizarNombre(nombreInformal)` (`santi-estevez`), es único y es a la vez el identificador del fotógrafo en las URL, el nombre de su logo (`datos/logos/santi-estevez.svg`) y **el nombre de su carpeta** (`fotos/santi-estevez/`). Debe coincidir SIEMPRE con la carpeta: lo calcula la aplicación (alta, importación y `cambiarNombreInformal()` en `backend/src/services/fotografo.service.ts`) y nunca se edita a mano. Cambiar el `nombreInformal` se hace con `cambiarNombreInformal()` (o `npm run fotografo:renombrar`): actualiza la BD y renombra la carpeta en la misma transacción (si el renombrado falla, la BD no cambia), rechaza nombres que coincidan con otro fotógrafo o con una carpeta existente, y borra el logo anterior para que se regenere. No hay endpoint para esto (aún no hay login). Al arrancar, el backend avisa en consola si a algún fotógrafo le falta su carpeta. **Usuarios:** la cuenta con la que se entra en la aplicación está en la tabla `usuarios` (nombre de `usuario`, `email` y `passwordHash`), separada de los datos del fotógrafo; cada fotógrafo referencia a su usuario (`fotografos.idUsuario`, obligatorio y único). Está separada para que en el futuro haya usuarios que no sean fotógrafos (empresas, academias…) con sus propios portfolios: tendrán su propia tabla con otra referencia a `usuarios`. Hoy el formulario del fotógrafo incluye el email y la contraseña, y `services/fotografo.service.ts` crea, modifica y elimina fotógrafo y usuario juntos, en la misma transacción. El nombre de `usuario` sirve para iniciar sesión (también vale el correo). Quien se registra lo elige (3 a 30 caracteres: letras sin tildes, números, `.`, `_`, `-`; se guarda en minúsculas; regla `USUARIO_NO_VALIDO`); en el alta desde `/admin` y en la importación se calcula (inicial del nombre + 3 primeras letras del primer apellido, sin tildes: `sest`; con sufijo numérico si se repite; `backend/src/utils/usuario.ts`). **El nombre de usuario de los demás nunca sale en la API**: solo `GET /api/sesion` devuelve el del propio usuario. **Administrador:** usuario especial `admin` (`usuarios.rol = 'administrador'`, único —índice único parcial—, sin fotógrafo), gestor de la aplicación. La BD lo crea al crearse, con la contraseña `admin` (`ADMINISTRADOR` en `db/conexion.ts`), que se puede cambiar. **Primer uso:** mientras su `fechaUltimoAcceso` esté vacía, `GET /api/estado` devuelve `{ primerUso: true }` y la web lleva a la bienvenida (`/admin/primer-uso`), que pide sus credenciales y ofrece cambiar la contraseña (`POST /api/admin/primer-uso`, solo una vez: regla `PRIMER_USO_COMPLETADO`); después se cambia en `/admin/contrasenya` (`PUT /api/admin/contrasenya`, con la actual). Lógica en `services/administrador.service.ts`. Al completar el primer uso el administrador queda con la sesión iniciada. **Sesiones** (`services/sesion.service.ts`): `POST /api/sesion` (usuario o correo + contraseña; 422 `USUARIO_CREDENCIALES_INCORRECTAS`, mismo mensaje si el usuario no existe, no tiene contraseña o no coincide), `GET /api/sesion` (`{ usuario: UsuarioSesion | null }`: `usuario`, `rol` y su `fotografo` si lo tiene) y `DELETE /api/sesion`; `GET /api/perfil` ("Mi perfil": sus datos como usuario y, si lo es, como fotógrafo) y `PUT /api/perfil/preferencias` (`{ temaPreferido: 'oscuro' | 'claro' | null }`), las dos 401 sin sesión (error `SinSesion` en `errores.ts`). El token aleatorio va en una cookie `sesion` `HttpOnly`, `SameSite=Lax` (y `Secure` si llega por HTTPS), 30 días; la tabla `sesiones` guarda solo su hash SHA-256 (borrar el usuario borra sus sesiones). La API usa CORS con `origin: true, credentials: true` y el frontend envía la cookie en todas las peticiones (interceptor `core/interceptors/con-credenciales.ts`). **Registro** (`POST /api/registro`, `registrarFotografo()`): usuario, correo y contraseña obligatorios (reglas `USUARIO_OBLIGATORIO`, `USUARIO_EMAIL_OBLIGATORIO`, `USUARIO_CONTRASENYA_OBLIGATORIA`) más los datos del fotógrafo; crea usuario, fotógrafo y carpeta y deja la sesión iniciada. **Permisos** (`routes/autorizacion.ts`): el administrador puede modificarlo todo; cualquier otro usuario, solo lo suyo (sus datos de usuario y fotógrafo, su foto, sus portfolios y colecciones, y en el futuro sus fotos); sin sesión, nada salvo registrarse. Consultar el catálogo es libre, salvo lo oculto (ver "Visibilidad"). Cada ruta de escritura llama al empezar a `exigirDuenyoOAdministrador(req, req.params.fotografo)` (el segmento se compara normalizado) o a `exigirAdministrador(req)` (alta de fotógrafos desde `/admin` y cambio de contraseña del administrador); `GET …/edicion` también exige ser el dueño, porque devuelve el correo. Sin sesión responde 401 (`SinSesion`) y sin permiso 403 (`SinPermiso`, `errores.ts`). En la web, `SesionService.puedeGestionar(fotografo)` / `esAdministrador()` deciden qué se muestra: los botones de mantenimiento (`fotografo-acciones`, `portfolio-acciones`, `coleccion-acciones` y las franjas "+ Nuevo portfolio", "+ Nueva colección" y "Gestionar fotos") siguen en las plantillas pero, sin permiso, no se muestran (`@if`); y los guards `puedeGestionarFotografo` y `soloAdministrador` (`core/guards/permisos.ts`, después de `urlCanonica`) devuelven a la portada a quien entra en un formulario sin permiso. Lo que protege de verdad es el backend. `db:importar --reemplazar` conserva al administrador. **Visibilidad** (tres estados, `portfolios.visibilidad` / `colecciones.visibilidad`: `'visible'` por defecto, `'bloqueado'` u `'oculto'`; tipo `Visibilidad`): su fotógrafo y el administrador lo ven y entran siempre; para los demás (con o sin sesión), **oculto** no existe (no sale en los listados ni en los totales —`portfolioCount`, `collectionCount`—, ni en `/api/colecciones` ni `/api/tags`, su página responde 404 y no da su portada) y **bloqueado** existe pero no se puede entrar (sale en los listados de su fotógrafo o portfolio y cuenta en los totales, con su nombre, pero sin portada —`coverPhotoUrl` vacía, y no da la del portfolio—, no sale en `/api/colecciones` ni `/api/tags`, su página responde **403 con `tipo: 'accesoRestringido'`** —error `AccesoRestringido` en `errores.ts`— y sus fotos no se sirven). Lo del portfolio vale para todas sus colecciones (la que manda es la más restrictiva). En el repositorio, `_VISIBLE` (existe para quien mira) y `_ACCESIBLE` (además puede entrar); las consultas de lectura reciben quién mira (`ve`: tipo `Vista`, `VER_TODO` por defecto, que es lo que usan los servicios; `vistaDe(req)` en `routes/autorizacion.ts` para las rutas `GET`, que deben pasarla siempre). Las fotos también se protegen: el middleware `soloFotosVisibles` (`routes/fotos-visibles.routes.ts`, delante de las miniaturas en `/photos`) solo sirve `/photos/<fotógrafo>/<portfolio>/<colección>/<fichero>` de una colección de la BD en la que pueda entrar quien la pide (404 en cualquier otro caso). Se cambia con `PUT …/portfolios/:portfolio/visibilidad` y `PUT …/colecciones/:coleccion/visibilidad` (cuerpo `{ visibilidad: 'visible' | 'bloqueado' | 'oculto' }`, o como antes `{ visible: true | false }`; 204; `cambiarVisibilidadPortfolio()` / `cambiarVisibilidadColeccion()`, operaciones `CAMBIAR_VISIBILIDAD_PORTFOLIO` / `CAMBIAR_VISIBILIDAD_COLECCION`), y la API devuelve en portfolios y colecciones `visibilidad` y, por compatibilidad, `visible` (= no oculto). La importación de JSON no lo contempla (todo entra visible). En la web, para quien no es su dueño, la tarjeta de lo bloqueado no es un enlace y muestra su nombre y el candado ("Bloqueado"/"Bloqueada"); su página muestra "Acceso restringido" (`shared/visibilidad/acceso-restringido.ts`, `esAccesoRestringido()` en `core/services/catalogo.ts`). Portfolio y colección: `nombre`, `descripcion` opcional y **`nombreNormalizado`** = `normalizarNombre(nombre)` (único dentro de su padre), que funciona igual que el `nombreInformalNormalizado` del fotógrafo: es su identificador en las URL (la API lo devuelve) y **el nombre de su carpeta**. Lo calcula la aplicación al guardar el nombre y nunca se edita a mano. Cambiar el nombre se hace con `renombrarPortfolio()` / `renombrarColeccion()` (`backend/src/services/portfolio.service.ts` y `coleccion.service.ts`, o `npm run portfolio:renombrar` / `coleccion:renombrar`) o con `editarPortfolio()` / `editarColeccion()` (endpoints `PUT`): recalculan el `nombreNormalizado` y, si cambia, renombran la carpeta en la misma transacción que la BD; rechazan nombres que coincidan con otro portfolio/colección del mismo padre o con una carpeta existente. Crear un portfolio/colección crea su carpeta y eliminarlo la borra, siempre con el `nombreNormalizado` como nombre. La portada de un portfolio es la de su colección de portada (`portfolios.idColeccionPortada`, que se elige con la estrella en "Gestionar colecciones") o, si no hay ninguna elegida, la de la primera colección; si esa colección no tiene fotos o el portfolio no tiene colecciones, no tiene portada (`coverPhotoUrl` vacía) y la web muestra "Sin fotos" o "Sin colecciones" en su lugar (igual que "Sin fotos" en una colección sin fotos). Una colección tiene `tags` (cuelgan dla colección, no de la foto) y fotos ordenadas. Las fotos están en `fotos/<nombreInformalNormalizado>/<nombreNormalizado portfolio>/<nombreNormalizado colección>/<nombreFichero>` y se sirven en `/photos/...` con esa misma ruta, que coincide con la de la web. Los ids y el `usuario` son internos: no aparecen ni en la API ni en las URL. **En las URL y en las carpetas nunca hay mayúsculas, tildes ni espacios.** **`normalizarNombre()`** (`backend/src/utils/normalizar-nombre.ts`) es el único helper que normaliza nombres (fotógrafos, portfolios y colecciones): quita los espacios de los extremos, pasa a minúsculas, "ñ" -> "ny", quita tildes y cambia cada grupo de espacios intermedios por un guion (`/lucia-martin/proyectos-personales/editorial`, "Montaña" -> `montanya`, "Irene Castaño" -> `irene-castanyo`). Está duplicada a propósito en el frontend (`core/utils/normalizar-nombre.ts`, solo para el guard de URL canónica) y debe mantenerse idéntica. Un nombre cuya forma normalizada no sirve como carpeta (contiene `/` o `\`, o empieza por `.`) se rechaza con la regla `NOMBRE_NO_VALIDO`. El backend la registra como función SQL (`db.function` en `db/conexion.ts`, porque `lower()` de SQLite solo convierte ASCII) para normalizar el segmento que llega en la URL antes de compararlo con la columna normalizada, así que la API acepta cualquier variante. En la web, el guard `core/guards/url-canonica.ts` (en las rutas con parámetros) redirige cualquier URL escrita con mayúsculas, tildes o espacios a su forma canónica (`/Santi Estévez` -> `/santi-estevez`, `/marta-vidal/encargos/montaña` -> `.../montanya`). "Ciudad de noche", "Ciudad-de noche" o "ciudad de noche" darían la misma URL y la misma carpeta: las reglas de negocio lo rechazan y el índice único sobre `nombreNormalizado` es la última defensa. Tampoco se controlan las mayúsculas en `nombreFichero` (las URL de `/photos/` usan el nombre real del fichero). Si `normalizarNombre()` cambia, habría que recalcular las columnas normalizadas y renombrar las carpetas (con una migración). La API usa el mismo vocabulario que la BD (`nombre`, `descripcion`, `fotos`, `nombreFichero`, `titulo`, `orden`, `ancho`, `alto`…); solo los campos calculados siguen en inglés (`coverPhotoUrl`, `photoCount`, `collectionCount`, `portfolioCount`, `logoUrl`, `url`).

- Fuente de verdad: la base de datos SQLite `backend/contenido/datos/BD/portfolio.db` (ruta configurable con `DB_PATH`; no versionada: `backend/contenido/` está en `.gitignore`). Esquema en `backend/src/db/conexion.ts`, notación lowerCamelCase: `usuarios` (PK `idUsuario`, `usuario` único, `email` opcional y único sin distinguir mayúsculas, `passwordHash`, `rol` `'usuario'`/`'administrador'` con un único administrador, `fechaUltimoAcceso`, `temaPreferido` `'oscuro'`/`'claro'`/NULL, `fotoActualizada`: cuándo se puso su foto de perfil, NULL si no tiene), `sesiones` (hash del token, `fechaExpiracion`), `fotografos` (PK `idFotografo`, FK `idUsuario` obligatoria y única, en cascada: borrar el usuario borra su fotógrafo; `nombreInformal`, `nombreInformalNormalizado` único, `nombre`, `primerApellido`, `segundoApellido`, `descripcion`), `portfolios` (PK `idPortfolio`, FK `idFotografo`, `nombreNormalizado`, `nombre`, `descripcion`, `idColeccionPortada` FK a `colecciones` ON DELETE SET NULL, `visibilidad` `'visible'`/`'bloqueado'`/`'oculto'`, `orden`; UNIQUE `(idFotografo, nombre)` e índice único `(idFotografo, nombreNormalizado)`), `colecciones` (PK `idColeccion`, FK `idPortfolio`, `nombreNormalizado`, `nombre`, `descripcion`, `idFotoPortada` FK a `fotos`, `visibilidad` `'visible'`/`'bloqueado'`/`'oculto'`, `orden`; UNIQUE `(idPortfolio, nombre)` e índice único `(idPortfolio, nombreNormalizado)`), `fotos` (PK `idFoto`, FK `idColeccion`, `nombreFichero` único por colección, `titulo`, `orden`, `ancho`, `alto`, `metadatos`: su EXIF completo en JSON, GPS incluido, o NULL) y `coleccionTags` (PK `idColeccion, tag`). Claves foráneas en cascada; los fotógrafos se listan por `idFotografo` (orden de alta). `usuarios`, `fotografos`, `portfolios`, `colecciones` y `fotos` tienen `fechaCreacion` y `fechaModificacion` (texto ISO 8601 UTC) mantenidas por la BD: DEFAULT y un trigger `<tabla>FechaModificacion` AFTER UPDATE. `passwordHash` guarda solo el hash scrypt (NULL si no tiene contraseña) y ni el email, ni el hash, ni el `usuario` salen nunca en la API pública (el email solo en `GET …/edicion`). La versión del esquema va en `PRAGMA user_version` (`VERSION_ESQUEMA`, hoy 19). Una BD nueva (versión 0) se crea con `ESQUEMA` y el administrador (`crearOAbrir()` en `db/conexion.ts`). **Migraciones** desde la versión 15: cada cambio de esquema sube la versión y añade en `MIGRACIONES` (`db/conexion.ts`) la de la anterior, que conserva los datos y se aplica en una transacción al abrir la BD (15 -> 16: `portfolios.idColeccionPortada`; 16 -> 17: `visible` en `portfolios` y `colecciones`; 17 -> 18: `fotos.metadatos`; 18 -> 19: `visibilidad` de tres estados en lugar de `visible` 0/1, en `portfolios` y `colecciones`); una BD de otra versión (anterior a la 15 o posterior) no se abre (el backend no arranca, para no perder datos). Al cambiar el esquema, actualizar a la vez `ESQUEMA` (BD nuevas) y `MIGRACIONES` (existentes). Cuidado al editar `conexion.ts` con `npm run dev` en marcha: el backend se recarga en cada guardado; pararlo antes de tocar el esquema. `organizacionFotos.json` ya no existe (estaba desfasado respecto a la BD y las carpetas): solo queda `npm run db:importar -- <fichero.json>` para cargas masivas puntuales (hoy, la única forma de dar de alta fotos en bloque). Ese JSON usa el mismo vocabulario: `OrganizacionFotos[]`, cada elemento `{ fotografo: { nombreInformal, usuario?, nombre, primerApellido, segundoApellido?, email?, descripcion }, portfolios: [{ nombre, descripcion?, colecciones: [{ nombre, descripcion?, tags, fotoPortada? (nombreFichero), fotos: [{ nombreFichero, titulo?, orden, ancho?, alto? }] }] }] }` (tipos en `backend/src/types/catalogo.ts`; `usuario` opcional para fijarlo si hay homónimos; la contraseña no se importa). Con `--reemplazar` borra antes todo el catálogo de la BD; con `--anyadir` lo añade al existente (pasando las mismas reglas, p. ej. un nombre informal repetido lo rechaza).
- Archivos de imagen reales: `backend/contenido/fotos/<nombreInformalNormalizado>/<nombreNormalizado del portfolio>/<nombreNormalizado dla colección>/<nombreFichero>` — deben coincidir exactamente con lo guardado en la BD, o las imágenes no se resolverán. Al importar un JSON las carpetas ya deben llamarse así (la importación no las crea ni las renombra).
- Logos de fotógrafo: nunca los aporta el usuario ni se anotan en la BD; los genera el backend. `GET /api/fotografos/:fotografo/logo` llama a `asegurarLogo` (`backend/src/services/logo.service.ts`), que sirve `backend/contenido/datos/logos/<nombreInformalNormalizado>.svg` (p. ej. `lucia-martin.svg`, `irene-castanyo.svg`) y, si no existe, lo genera con el `nombreInformal` como firma. Al cambiar el `nombreInformal`, `cambiarNombreInformal()` borra el logo anterior y se genera uno nuevo en la siguiente petición. El logo es un SVG tipo firma en letra manuscrita Mrs Saint Delafield con un subrayado de plumilla, con el texto convertido a trazos (un `<img>` no puede cargar fuentes) y tinta `#f2f1ed` para el fondo oscuro. La fuente (OFL) está en `backend/assets/fonts` y se copia a la imagen Docker. La API expone solo `logoUrl`.
- **Fotos en AVIF** (`utils/foto-avif.ts`): las fotos de las colecciones no se guardan como llegan, sino convertidas a AVIF de alta resolución, y **la original no se conserva**: se gira según su orientación EXIF, se reduce para que su lado largo no pase de 3840 px (`LADO_MAXIMO_FOTO`, una pantalla 4K completa; nunca se amplía), conserva su perfil de color si es RGB (Display P3, Adobe RGB…: pasarla a sRGB recortaría los colores más saturados; sin perfil, en CMYK o en blanco y negro se pasa a sRGB; `conPerfilDeColor()`, que usan también las miniaturas), **conservando su EXIF salvo la ubicación GPS** (ver "Metadatos EXIF"), con calidad 80 y el color sin submuestrear (4:4:4). Se guarda con el nombre del fichero subido y la extensión `.avif` (`nombreAvif()`: "Playa.jpg" -> `Playa.avif`), y en la BD con el ancho y el alto de la versión guardada. Las calidades se eligieron comparando al 100 % con las originales (también fotos con mucho grano): por debajo se suaviza el grano a la vista. Las fotos de antes de este cambio (o las que entren con `db:importar`) se convierten con `npm run fotos:convertir` (`scripts/convertir-fotos.ts`, `convertirFotoGuardada()` en `foto.service.ts`, operación `CONVERTIR_FOTO`): sustituye el fichero, actualiza nombre, ancho y alto en la BD (con `-2`, `-3`… si el nombre `.avif` ya está ocupado en la colección) y borra la original; se puede repetir, solo convierte lo que aún no es AVIF. Miniaturas: la web no muestra las fotos a 3840 px en las cuadrículas (el navegador las reduciría al vuelo con un filtro rápido, con dientes de sierra y grano), sino una miniatura AVIF de 960 px de ancho (calidad 75) que genera el backend con `sharp` (filtro Lanczos). Se pide como la foto más `?ancho=960`; `?ancho=3840` es la foto tal cual (solo de una foto aún sin convertir se genera y guarda su versión grande); otro ancho: 400. Se genera por adelantado, para que se sirva al instante (generarla al pedirla tarda de 0,5 a 1 s por foto): al subir la foto (`anyadirFoto()` espera a `prepararMiniatura()`) y, al arrancar, en segundo plano y de una en una, las que falten (`generarMiniaturasPendientes()`); si aun así falta, se genera al pedirla. Va en `datos/miniaturas/960/<misma ruta>`, una caché interna como los logos (en Docker, en la carpeta de datos, `DATOS_PATH`): se regenera si la foto es más reciente y se puede borrar sin perder nada. Lógica en `services/miniatura.service.ts` (con `sharp.cache(false)`, porque su caché deja los ficheros abiertos y en Windows impide renombrar o borrar después las fotos) y `routes/miniaturas.routes.ts` (middleware delante de `express.static` en `/photos`; si no se puede generar, sirve la foto; `express` no conoce `.avif`, así que el tipo `image/avif` se pone a mano, también en `express.static` con `tipoAvif`). Al eliminar una foto, colección, portfolio o fotógrafo se borran sus miniaturas (`borrarMiniaturas()`); al **renombrar** un fotógrafo, portfolio o colección **se mueven** con su carpeta (`moverMiniaturas()`), porque siguen valiendo: si se borraran, cada una tardaría casi un segundo en regenerarse al pedirla y la cuadrícula se iría llenando poco a poco (si no se pueden mover, se borran y se regeneran ya, en segundo plano); y al arrancar se borra lo que ya no se usa de `datos/miniaturas` (`borrarAnchosObsoletos()`: carpetas de otros anchos y ficheros que no son AVIF, de versiones anteriores). En la web, la directiva `shared/foto-reducida/` (`<img [appFotoReducida]="url" tamanyos="…">`) pone `src` (la miniatura), `srcset` con la miniatura (`960w`) y la foto (`3840w`; la imagen debe tener el ancho fijado por CSS, porque en una vertical no es su ancho real) y `sizes`; el navegador usa la miniatura si basta para el tamaño en pantalla y, si no, la foto. La usan todas las imágenes de fotos y portadas; el visor (`shared/lightbox/`) muestra siempre la foto (`?ancho=3840`). `/photos` no sirve nada con un segmento que empiece por punto (`dotfiles: 'ignore'`; por defecto `express.static` sí serviría los ficheros de dentro de una carpeta con punto, como las papeleras o las subidas a medias).
- **Metadatos EXIF** (`utils/metadatos-foto.ts`, librería `exif-reader`): al convertir una foto a AVIF (subida y `fotos:convertir`), su EXIF (cámara, objetivo, exposición, fecha, autor…) se conserva en la AVIF grande, **salvo la ubicación GPS** (`quitarGps()` vacía ese grupo en su sitio, sin volver a codificar: la foto la puede descargar cualquiera que la vea), y se guarda **completo, GPS incluido, en `fotos.metadatos`** (JSON de los grupos `Image`, `Photo`, `Iop` y `GPSInfo`; sin la miniatura incrustada ni los datos binarios grandes como MakerNote; fechas sin zona horaria, la hora de la cámara), para consultarlos sin abrir la foto, también desde una miniatura (que no lleva EXIF). La API da con cada foto `metadatos` (tipo `MetadatosFoto`: `camara`, `objetivo`, `distanciaFocal`, `distanciaFocal35mm`, `apertura`, `exposicion`, `iso`, `compensacionExposicion`, `fechaToma`, `autor`, `copyright`, `software`; solo los que tenga, `resumirMetadatos()`), **nunca la ubicación**. Aún no se muestran en la web. Las fotos subidas antes no tienen (se guardaron sin EXIF y su original no se conserva). La orientación del EXIF queda en la normal porque la foto ya se gira al convertirla.
- Tipos compartidos conceptualmente (no compartidos por código, ya que son dos paquetes npm separados): `backend/src/types/catalogo.ts` y `frontend/src/app/core/models/catalogo.model.ts`. Si se cambia la forma del JSON hay que actualizar ambos.

### Reglas de negocio (`backend/src/reglas/`)

Todo lo que la aplicación no permite ("un fotógrafo no puede tener dos portfolios con el mismo nombre") se gestiona en un único módulo:

- `catalogo.ts` — **único sitio donde se definen las reglas y se redactan sus textos**: `REGLAS` (código -> mensaje, p. ej. `PORTFOLIO_NOMBRE_DUPLICADO: 'Ya existe otro portfolio con el mismo nombre ("{nombre}") para este fotógrafo.'`) y `OPERACIONES` (código -> descripción en infinitivo de lo que se intentaba hacer, p. ej. `CREAR_PORTFOLIO: 'Crear el portfolio "{nombre}" del fotógrafo "{fotografo}"'`). Los `{campo}` se rellenan con los datos al incumplirse.
- `regla-incumplida.ts` — el error `ReglaNegocioIncumplida` (código, datos, mensaje de la regla y, opcionalmente, la operación intentada), `exigir(condición, código, datos)` / `incumplir(código, datos)` para lanzarlo, y `enOperacion(códigoOperación, datos, fn)` que envuelve una acción para que cualquier regla incumplida dentro salga acompañada de lo que se intentaba (se conserva la operación más interna). `toJSON()` es la respuesta de la API y `aTexto()` la salida de consola.
- `validaciones.ts` — `validadorCatalogo(db)`: las comprobaciones que consultan la BD (nombres de portfolio/colección duplicados comparados en su forma normalizada, nombres que no sirven como carpeta, carpeta de destino ocupada al renombrar, nombre informal repetido, y en `usuario()` las de la cuenta —correo con formato válido y no repetido, nombre de usuario no repetido, longitud mínima de la contraseña: reglas `USUARIO_*`—, fichero repetido en una colección, foto de portada inexistente, tags repetidos, obligatorios…). Aceptan el id del propio elemento (`excluir`) para las modificaciones. El repositorio exporta `validar` (validador sobre la conexión principal).

Todo lo que escribe en el catálogo debe validar antes de guardar y envolverse en su operación: la importación (`db/importar.ts`: `CREAR_FOTOGRAFO`, `CREAR_PORTFOLIO`, `CREAR_COLECCION`, `ANYADIR_FOTO`) `cambiarNombreInformal()` (`CAMBIAR_NOMBRE_INFORMAL`) y `renombrarPortfolio()` / `renombrarColeccion()` (`RENOMBRAR_PORTFOLIO`, `RENOMBRAR_COLECCION`), `crearPortfolio()` / `editarPortfolio()` / `ordenarPortfolios()` / `eliminarPortfolio()` (`CREAR_PORTFOLIO`, `EDITAR_PORTFOLIO`, `ORDENAR_PORTFOLIOS`, `ELIMINAR_PORTFOLIO`), `crearColeccion()` / `editarColeccion()` / `ordenarColecciones()` / `eliminarColeccion()` (`CREAR_COLECCION`, `EDITAR_COLECCION`, `ORDENAR_COLECCIONES`, `ELIMINAR_COLECCION`), `anyadirFoto()` / `ordenarFotos()` / `eliminarFoto()` (`ANYADIR_FOTO`, `ORDENAR_FOTOS`, `ELIMINAR_FOTO`); cualquier endpoint de escritura futuro, igual. Las restricciones UNIQUE/NOT NULL de la BD se mantienen como última defensa. Para añadir una regla: código y mensaje en `catalogo.ts`, comprobación en `validaciones.ts` (o `exigir` donde toque) y un test en `reglas/reglas.test.ts`.

Una regla incumplida en la API se responde con **422** y este cuerpo: `{ tipo: "reglaNegocioIncumplida", operacion: { codigo, descripcion }, regla: { codigo, mensaje }, message }` (`message` = "No se ha podido <operación>. <regla>"). En los comandos (`db:importar`, `fotografo:renombrar`, `portfolio:renombrar`, `coleccion:renombrar`) se muestra la operación y la regla en consola y no se guarda nada (transacción).

### Frontend (`frontend/src/app/`)

Angular standalone (sin `NgModule`), routing con `loadComponent` (lazy):

- `core/config/api.config.ts` — URL base de la API.
- `features/fotografo-list/` — página raíz (`/`), listado de fotógrafos (solo el título y las tarjetas). El alta de fotógrafos desde el administrador (`/admin/fotografos/nuevo`) y el cambio de contraseña del administrador (`/admin/contrasenya`) no tienen enlace en la interfaz: se llega por su dirección. Los fotógrafos se dan de alta registrándose.
- **Marco de las fotos** (`core/services/marco.ts`, `MarcoService`, y `shared/selector-marco/`, con los estilos de `selector-tema`): "Con marco" / "Sin marco" en la franja superior, junto al tema, **solo en la página de una colección** (`enColeccion` en `app.ts`: ruta del catálogo con `:coleccion`). - `shared/compartir/` — icono "compartir" a la derecha del título (`cabecera__titulo` en `_cabecera.scss`) de las páginas de fotógrafo, portfolio y colección (no en su vista limpia): abre un diálogo ("Comparte este enlace si quieres compartir esta página") con el enlace de la página **en su vista limpia** (`enlaceVistaLimpia()` de `core/services/vista-limpia.ts`: `origin + ruta + ?limpia=true`), un icono para copiarlo (`navigator.clipboard` en contexto seguro; servida por http, como en el NAS en la red local, `execCommand('copy')` seleccionando el campo; si falla, lo deja seleccionado) y "Cerrar".

- `features/perfil/` — "Mi perfil" (`/perfil`): sus datos como usuario (cuenta) y, si lo es, como fotógrafo (sección "Datos personales y preferencias", con su firma y totales), con "Editar cuenta" en la sección "Cuenta" y enlaces a su página y a editar sus datos. `features/cuenta-form/` — "Editar cuenta" (`/perfil/cuenta`, con sesión), **un único formulario con un único "Guardar cambios"**: en la sección "Cuenta", el nombre de usuario (mismas reglas que al registrarse, en minúsculas; el del administrador no se puede cambiar, regla `USUARIO_ADMINISTRADOR_NO_RENOMBRABLE`) y, justo debajo, "Cambiar contraseña", que despliega la actual y la nueva, repetida ("No cambiar la contraseña" lo pliega y entonces ni se valida ni se envía); en "Preferencias", el tema preferido (sin preferencia, oscuro o claro). Todo va en una sola petición, `PUT /api/perfil/cuenta` (`{ usuario, temaPreferido, contrasenya?: { contrasenyaActual, contrasenyaNueva } }`, 204; `editarCuenta()` en `services/sesion.service.ts`, operación `EDITAR_CUENTA`), que lo valida todo y lo guarda en una transacción: **o todo o nada** (antes eran dos botones y era fácil cambiar la contraseña dejando el usuario sin guardar). "Mi perfil" y "Editar cuenta" exigen sesión (guard `core/guards/con-sesion.ts`; sin ella, a la portada). ### Diseño / estilo

Sistema de diseño propio en SCSS (sin Angular Material ni Tailwind, por decisión explícita): tokens como custom properties en `frontend/src/styles.scss`. **Dos temas**: el oscuro (predeterminado) en `:root` y el claro en `:root[data-tema='claro']`, que redefine los mismos tokens; se elige en la franja superior (`shared/selector-tema/`, `core/services/tema.ts`, guardado en `localStorage` y aplicado ya en `index.html` para que no parpadee). Los componentes usan siempre tokens, nunca colores fijos (`--color-peligro*` para eliminar y errores, `--color-velo` para el fondo de los diálogos, `--filtro-logo`, que invierte en el tema claro los logos, generados con tinta clara); el visor de fotos (`shared/lightbox/`) también sigue el tema, con su propio fondo casi opaco (`--color-visor-fondo`). Tema oscuro: paleta neutra para que las fotos destaquen; tipografía serif `Cormorant Garamond` para títulos + `Inter` para UI, cargadas vía Google Fonts en `index.html`). Los estilos de cada componente son locales a su carpeta (`*.scss` junto al componente); el presupuesto de `angular.json` avisa si los de un componente pasan de 6 kB (error a partir de 8 kB). La cabecera a todo el ancho de las páginas de fotógrafo, portfolio y colección (datos a la izquierda —etiqueta con el tipo y el número de elementos, nombre y descripción—, mantenimiento a la derecha y línea separadora difuminada debajo, y bajo ella la franja `cabecera-barra` con "Gestionar portfolios" y "+ Nuevo portfolio", "Gestionar colecciones" y "+ Nueva colección", o "Gestionar fotos") está en el parcial `shared/estilos/_cabecera.scss`, que cada página incluye con `@use`. Los estilos comunes de los formularios están igual en `shared/estilos/_formulario.scss`.

### Despliegue con Docker (NAS)

`docker-compose.yml` en la raíz levanta dos servicios en la red interna `portfolio`, usando imágenes ya construidas en vez de build local:

- `backend` — imagen `ghcr.io/sestevez5/portoliosfotograficos-backend:latest`. No publica puerto al host; solo es accesible desde `frontend` a través de la red de Docker Compose.
- `frontend` — imagen `ghcr.io/sestevez5/portoliosfotograficos-frontend:latest`. Publica un único puerto al host (`FRONTEND_PORT`, por defecto 8080).

Las imágenes se construyen y publican automáticamente en GitHub Container Registry (GHCR) mediante `.github/workflows/docker-publish.yml` en cada push a `main` (tags `:latest` y `:<sha>`). Por eso el NAS **no necesita el código fuente**: solo `docker-compose.yml`, `.env` y las carpetas de fotos y datos (ver más abajo). Si el paquete de GHCR está en privado, hay que hacer `docker login ghcr.io` una vez en el NAS con un token con permiso `read:packages` antes de poder hacer `pull` (o marcar el paquete como público desde la configuración de GitHub).

`docker-compose.override.yml` (no se copia al NAS) añade `build: context: ...` a ambos servicios y Docker Compose lo aplica automáticamente cuando está presente junto a `docker-compose.yml` — así en local, con el repo completo, `docker compose build`/`up` siguen construyendo las imágenes desde los Dockerfiles en vez de tirar de GHCR. Los Dockerfiles (`backend/Dockerfile`, `frontend/Dockerfile`) son multi-stage: el backend hace `npm run build` + `npm ci --omit=dev` + `node dist/index.js`; el frontend hace `ng build` y sirve `dist/frontend/browser` con nginx.

`frontend/nginx.conf` hace de proxy inverso: sirve los estáticos de Angular y reenvía `/api/` y `/photos/` al servicio `backend:3000`, de forma que el navegador solo ve un origen. Por eso en build de producción `API_BASE_URL` debe ser `''` (ruta relativa) en vez de `http://localhost:3000`: `angular.json` usa `fileReplacements` en la configuración `production` para sustituir `api.config.ts` por `api.config.prod.ts` automáticamente en cualquier `ng build` (o `npm run build`) sin flags adicionales. En desarrollo (`ng serve`) se sigue usando `api.config.ts` tal cual.

**Desde el NAS se montan dos carpetas, hermanas, dentro de la carpeta `contenido` del proyecto** (`<proyecto>/contenido/fotos` y `<proyecto>/contenido/datos`, como en desarrollo `backend/contenido/`): la de fotos (bind mount de `FOTOS_PATH` en `/app/fotos`, que el backend usa por `FOTOS_DIR`, fijada en el Dockerfile) y la de datos de la aplicación (`DATOS_PATH` en `/app/datos`, que el backend usa por `DATOS_DIR`, también fijada en el Dockerfile: sin ella usaría `/app/contenido/datos`, sin montar, como pasaba en la 2.3.0; base de datos `BD/portfolio.db`, `logos/`, `miniaturas/` y `avatares/`). Las dos deben ser escribibles por el contenedor. Están juntas para que una instantánea o copia de la carpeta `contenido` guarde a la vez la BD y las fotos, que deben corresponderse; la de datos no va dentro de la de fotos, y es interna (no se toca a mano con la aplicación en marcha: con WAL, `portfolio.db` sola puede estar incompleta). **Si `DATOS_PATH` no está definida**, `/app/datos` va en el volumen con nombre `datos-internos`, gestionado por Docker y no visible en el host (lo que se usaba hasta la 2.1; sobrevive a `pull`/`up -d`, se pierde con `docker compose down -v` o borrando el volumen); se mantiene por compatibilidad y para la preproducción en Windows. Pasar de una a otra: `docker compose stop backend`, `docker compose cp backend:/app/datos/. <DATOS_PATH>/`, definir `DATOS_PATH` en `.env` y `docker compose up -d`. En el primer arranque la BD se crea vacía (el backend crea las subcarpetas). Nada de `backend/contenido` se hornea en la imagen (`backend/.dockerignore` la excluye) ni se versiona. Cargar una BD existente: con el backend parado, copiar `portfolio.db` a `<DATOS_PATH>/BD/` (o, con el volumen, `docker compose cp portfolio.db backend:/app/datos/BD/portfolio.db`), sin `-wal`/`-shm` y consolidando antes el WAL. Los logos y las miniaturas no hace falta copiarlos: se regeneran al pedirlos. `better-sqlite3` es un módulo nativo: el Dockerfile instala sus dependencias en una etapa `deps` con `python3 make g++` por si hay que compilarlo (p. ej. NAS ARM) y copia solo `node_modules` a la imagen final. Las rutas en el host del NAS se configuran con las variables `FOTOS_PATH` (obligatoria) y `DATOS_PATH` en un fichero `.env` (no versionado; ver `.env.example`) junto con `FRONTEND_PORT`.

Despliegue típico en el NAS (solo con `docker-compose.yml`, `.env` y las carpetas de fotos y datos, sin el resto del repo): `cp .env.example .env` (ajustar rutas), `docker compose pull`, `docker compose up -d`. Para desplegar una versión nueva más adelante: `docker compose pull && docker compose up -d` de nuevo.

## Versionado

Versionado semántico `MAYOR.MENOR.PARCHE` (semver), una única versión para todo el monorepo:

- **MAYOR**: cambios incompatibles (p. ej. cambios en la organización de `datos/` que obligan a migrar los datos del NAS, o rutas de la API que desaparecen).
- **MENOR**: funcionalidad nueva compatible hacia atrás.
- **PARCHE**: correcciones sin cambios de funcionalidad.

Al publicar una versión: actualizar `version` en `backend/package.json` y `frontend/package.json` (`npm version X.Y.Z --no-git-tag-version` en cada paquete, que también actualiza el lockfile) y `fechaVersion` (AAAA-MM-DD) en `backend/package.json` (la fecha que muestra "Acerca de"), regenerar la documentación (`node docs/generar-html.mjs`, que actualiza también el manual de la web), añadir la entrada en `CHANGELOG.md`, hacer commit en `develop`, fusionar en `main` y crear el tag anotado `vX.Y.Z` en `main`. El desarrollo diario va en `develop`; `main` solo recibe versiones.

## Notas para seguir desarrollando

- Guía para colaboradores (preparar el entorno, preproducción con Docker con su propia BD y carpeta de fotos, flujo de git): `CONTRIBUTING.md`. Mantenerla al día si cambian comandos, variables o el despliegue.
- Las fotos actuales son contenido de prueba generado como placeholders de color — hay que sustituirlas por fotos reales.
- **Desde que existe el alta de fotógrafos, la BD es la única fuente de verdad**: y no está en el repositorio. `db:importar -- <fichero> --reemplazar` borraría el catálogo existente. Hacer copias de `portfolio.db` antes de esas operaciones.
- **Las escrituras están protegidas por permisos** (ver "Permisos" en el modelo de datos): sin sesión no se puede modificar nada y cada usuario solo lo suyo. Pendiente antes de publicar fuera de la red local: servirla por **https** (la cookie de sesión lleva `Secure` solo si la petición llega por https, y la cámara de la foto de perfil lo exige) y restringir el CORS (hoy `origin: true`, pensado para desarrollo).
- Copias de seguridad: en local basta con copiar `portfolio.db` con el backend parado (con WAL activo existen también `portfolio.db-wal`/`-shm` mientras corre). En Docker con `DATOS_PATH`, una instantánea (Btrfs) de la carpeta del proyecto copia a la vez BD (con su `-wal`) y fotos de forma coherente; copiar ficheros sueltos con el backend en marcha no es seguro. Con o sin ella, copia en caliente de la BD con `docker compose exec backend node -e "require('better-sqlite3')('datos/BD/portfolio.db').backup('datos/BD/copia.db').then(() => console.log('ok'))"` y `docker compose cp backend:/app/datos/BD/copia.db .`. Las fotos se copian directamente desde su carpeta del NAS.
- `GET /api/colecciones` sin filtro devuelve todas las colecciones; con miles de colecciones (probado con 1.000 fotógrafos / 100.000 fotos: ~640 KB, ~40 ms) convendría paginarlo si se empieza a usar desde la interfaz. El resto de rutas responde en pocos ms a esa escala.
- Repositorio git inicializado, con remoto en GitHub (`https://github.com/sestevez5/portoliosfotograficos.git`, rama `main`).
