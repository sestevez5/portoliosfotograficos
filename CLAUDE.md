# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Resumen del proyecto

Portfolio fotográfico elegante y minimalista. Monorepo con dos paquetes independientes:

- `backend/` — API sencilla en Node.js + Express + TypeScript (ESM) que sirve el catálogo de colecciones/fotos desde una base de datos SQLite y las imágenes como archivos estáticos.
- `frontend/` — Aplicación Angular (standalone components, sin librería de UI) que consume esa API y presenta las fotos.

El catálogo (fotógrafos, portfolios, colecciones, fotos, tags) vive en una base de datos **SQLite** (`backend/datos/BD/portfolio.db`, acceso con `better-sqlite3`). Las imágenes siguen siendo ficheros en `backend/datos/fotos`. **Toda la carpeta `backend/datos` (BD, fotos y logos) está en `.gitignore`**: el repositorio refleja siempre una base de datos vacía y los datos viven solo en cada instalación (en el NAS, en el volumen montado). Un clon nuevo arranca con la BD vacía (se crea sola).

## Comandos

### Backend (`backend/`)

```
npm install         # instalar dependencias
npm run dev          # servidor de desarrollo con recarga (tsx watch), puerto 3000
npm test             # tests (node:test + tsx): reglas de negocio y respuesta de errores de la API
npm run typecheck    # tsc --noEmit
npm run db:importar -- <fichero.json>   # carga masiva de un catálogo en JSON si la BD está vacía (--reemplazar para sustituirlo, --anyadir para añadirlo al actual)
npm run fotografo:renombrar -- <fotógrafo> "<nuevo nombreInformal>"   # cambia el nombreInformal y renombra su carpeta
npm run portfolio:renombrar -- <fotógrafo> <portfolio> "<nuevo nombre>"          # cambia el nombre del portfolio y renombra su carpeta
npm run coleccion:renombrar -- <fotógrafo> <portfolio> <colección> "<nuevo nombre>"      # ídem para una colección
npm run build         # compila a dist/ (tsc)
npm start             # ejecuta dist/index.js (requiere build previo)
```

### Frontend (`frontend/`)

```
npm install                     # instalar dependencias
npm start                        # ng serve, puerto 4200
npm run build                    # build de producción
npx ng test --watch=false        # ejecuta toda la suite (Vitest) una vez
npx ng test --watch=false -- <patrón>   # ejecutar un subconjunto de tests por nombre/archivo
```

El frontend espera la API en `http://localhost:3000` (constante `API_BASE_URL` en `frontend/src/app/core/config/api.config.ts`). Para probar la app completa hay que tener backend y frontend corriendo a la vez.

## Arquitectura

### Modelo de datos

Jerarquía: **fotógrafo → portfolios → colecciones → fotos**. Fotógrafo: `nombreInformal` (obligatorio; p. ej. "Santi Estévez", texto con el que se dibuja su logo), `nombreInformalNormalizado`, `nombre`, `primerApellido` (obligatorio), `segundoApellido` y `email` opcionales, `descripcion`. **`nombreInformalNormalizado`** es `normalizarNombre(nombreInformal)` (`santi-estevez`), es único y es a la vez el identificador del fotógrafo en las URL, el nombre de su logo (`datos/logos/santi-estevez.svg`) y **el nombre de su carpeta** (`datos/fotos/santi-estevez/`). Debe coincidir SIEMPRE con la carpeta: lo calcula la aplicación (alta, importación y `cambiarNombreInformal()` en `backend/src/services/fotografo.service.ts`) y nunca se edita a mano. Cambiar el `nombreInformal` se hace con `cambiarNombreInformal()` (o `npm run fotografo:renombrar`): actualiza la BD y renombra la carpeta en la misma transacción (si el renombrado falla, la BD no cambia), rechaza nombres que coincidan con otro fotógrafo o con una carpeta existente, y borra el logo anterior para que se regenere. No hay endpoint para esto (aún no hay login). Al arrancar, el backend avisa en consola si a algún fotógrafo le falta su carpeta. **Usuarios:** la cuenta con la que se entra en la aplicación está en la tabla `usuarios` (nombre de `usuario`, `email` y `passwordHash`), separada de los datos del fotógrafo; cada fotógrafo referencia a su usuario (`fotografos.idUsuario`, obligatorio y único). Está separada para que en el futuro haya usuarios que no sean fotógrafos (empresas, academias…) con sus propios portfolios: tendrán su propia tabla con otra referencia a `usuarios`. Hoy el formulario del fotógrafo incluye el email y la contraseña, y `services/fotografo.service.ts` crea, modifica y elimina fotógrafo y usuario juntos, en la misma transacción. El nombre de `usuario` sirve para iniciar sesión (también vale el correo). Quien se registra lo elige (3 a 30 caracteres: letras sin tildes, números, `.`, `_`, `-`; se guarda en minúsculas; regla `USUARIO_NO_VALIDO`); en el alta desde `/admin` y en la importación se calcula (inicial del nombre + 3 primeras letras del primer apellido, sin tildes: `sest`; con sufijo numérico si se repite; `backend/src/utils/usuario.ts`). **El nombre de usuario de los demás nunca sale en la API**: solo `GET /api/sesion` devuelve el del propio usuario. **Administrador:** usuario especial `admin` (`usuarios.rol = 'administrador'`, único —índice único parcial—, sin fotógrafo), gestor de la aplicación. La BD lo crea al crearse, con la contraseña `admin` (`ADMINISTRADOR` en `db/conexion.ts`), que se puede cambiar. **Primer uso:** mientras su `fechaUltimoAcceso` esté vacía, `GET /api/estado` devuelve `{ primerUso: true }` y la web lleva a la bienvenida (`/admin/primer-uso`), que pide sus credenciales y ofrece cambiar la contraseña (`POST /api/admin/primer-uso`, solo una vez: regla `PRIMER_USO_COMPLETADO`); después se cambia en `/admin/contrasenya` (`PUT /api/admin/contrasenya`, con la actual). Lógica en `services/administrador.service.ts`. Al completar el primer uso el administrador queda con la sesión iniciada. **Sesiones** (`services/sesion.service.ts`): `POST /api/sesion` (usuario o correo + contraseña; 422 `USUARIO_CREDENCIALES_INCORRECTAS`, mismo mensaje si el usuario no existe, no tiene contraseña o no coincide), `GET /api/sesion` (`{ usuario: UsuarioSesion | null }`: `usuario`, `rol` y su `fotografo` si lo tiene) y `DELETE /api/sesion`; `GET /api/perfil` ("Mi perfil": sus datos como usuario y, si lo es, como fotógrafo) y `PUT /api/perfil/preferencias` (`{ temaPreferido: 'oscuro' | 'claro' | null }`), las dos 401 sin sesión (error `SinSesion` en `errores.ts`). El token aleatorio va en una cookie `sesion` `HttpOnly`, `SameSite=Lax` (y `Secure` si llega por HTTPS), 30 días; la tabla `sesiones` guarda solo su hash SHA-256 (borrar el usuario borra sus sesiones). La API usa CORS con `origin: true, credentials: true` y el frontend envía la cookie en todas las peticiones (interceptor `core/interceptors/con-credenciales.ts`). **Registro** (`POST /api/registro`, `registrarFotografo()`): usuario, correo y contraseña obligatorios (reglas `USUARIO_OBLIGATORIO`, `USUARIO_EMAIL_OBLIGATORIO`, `USUARIO_CONTRASENYA_OBLIGATORIA`) más los datos del fotógrafo; crea usuario, fotógrafo y carpeta y deja la sesión iniciada. **Permisos** (`routes/autorizacion.ts`): el administrador puede modificarlo todo; cualquier otro usuario, solo lo suyo (sus datos de usuario y fotógrafo, su foto, sus portfolios y colecciones, y en el futuro sus fotos); sin sesión, nada salvo registrarse. Consultar el catálogo es libre, salvo lo oculto (ver "Visibilidad"). Cada ruta de escritura llama al empezar a `exigirDuenyoOAdministrador(req, req.params.fotografo)` (el segmento se compara normalizado) o a `exigirAdministrador(req)` (alta de fotógrafos desde `/admin` y cambio de contraseña del administrador); `GET …/edicion` también exige ser el dueño, porque devuelve el correo. Sin sesión responde 401 (`SinSesion`) y sin permiso 403 (`SinPermiso`, `errores.ts`). En la web, `SesionService.puedeGestionar(fotografo)` / `esAdministrador()` deciden qué se muestra: los botones de mantenimiento (`fotografo-acciones`, `portfolio-acciones`, `coleccion-acciones` y las franjas "+ Nuevo portfolio", "+ Nueva colección" y "Gestionar fotos") siguen en las plantillas pero, sin permiso, no se muestran (`@if`); y los guards `puedeGestionarFotografo` y `soloAdministrador` (`core/guards/permisos.ts`, después de `urlCanonica`) devuelven a la portada a quien entra en un formulario sin permiso. Lo que protege de verdad es el backend. `db:importar --reemplazar` conserva al administrador. **Visibilidad:** un portfolio o una colección se pueden ocultar a los demás usuarios (`portfolios.visible` / `colecciones.visible`, 1 por defecto). Lo oculto solo lo ven su fotógrafo y el administrador; para los demás (con o sin sesión) no existe: no sale en los listados ni en los totales (`portfolioCount`, `collectionCount`), ni en `/api/colecciones` ni `/api/tags`, su página responde 404 y no da su portada (la del portfolio pasa a ser la de la primera colección que sí se ve). Un portfolio oculto oculta todas sus colecciones. Las consultas de lectura del repositorio reciben quién mira (`ve`: tipo `Vista`, `VER_TODO` por defecto, que es lo que usan los servicios; `vistaDe(req)` en `routes/autorizacion.ts` para las rutas `GET`, que deben pasarla siempre). Las fotos también se protegen: el middleware `soloFotosVisibles` (`routes/fotos-visibles.routes.ts`, delante de las miniaturas en `/photos`) solo sirve `/photos/<fotógrafo>/<portfolio>/<colección>/<fichero>` de una colección de la BD que pueda ver quien la pide (404 en cualquier otro caso). Se cambia con `PUT …/portfolios/:portfolio/visibilidad` y `PUT …/colecciones/:coleccion/visibilidad` (cuerpo `{ visible: true | false }`; 204; `cambiarVisibilidadPortfolio()` / `cambiarVisibilidadColeccion()`, operaciones `CAMBIAR_VISIBILIDAD_PORTFOLIO` / `CAMBIAR_VISIBILIDAD_COLECCION`), y la API devuelve `visible` en portfolios y colecciones. La importación de JSON no lo contempla (todo entra visible). Portfolio y colección: `nombre`, `descripcion` opcional y **`nombreNormalizado`** = `normalizarNombre(nombre)` (único dentro de su padre), que funciona igual que el `nombreInformalNormalizado` del fotógrafo: es su identificador en las URL (la API lo devuelve) y **el nombre de su carpeta**. Lo calcula la aplicación al guardar el nombre y nunca se edita a mano. Cambiar el nombre se hace con `renombrarPortfolio()` / `renombrarColeccion()` (`backend/src/services/portfolio.service.ts` y `coleccion.service.ts`, o `npm run portfolio:renombrar` / `coleccion:renombrar`) o con `editarPortfolio()` / `editarColeccion()` (endpoints `PUT`): recalculan el `nombreNormalizado` y, si cambia, renombran la carpeta en la misma transacción que la BD; rechazan nombres que coincidan con otro portfolio/colección del mismo padre o con una carpeta existente. Crear un portfolio/colección crea su carpeta y eliminarlo la borra, siempre con el `nombreNormalizado` como nombre. La portada de un portfolio es la de su colección de portada (`portfolios.idColeccionPortada`, que se elige con la estrella en "Gestionar colecciones") o, si no hay ninguna elegida, la de la primera colección; si esa colección no tiene fotos o el portfolio no tiene colecciones, no tiene portada (`coverPhotoUrl` vacía) y la web muestra "Sin fotos" o "Sin colecciones" en su lugar (igual que "Sin fotos" en una colección sin fotos). Una colección tiene `tags` (cuelgan dla colección, no de la foto) y fotos ordenadas. Las fotos están en `datos/fotos/<nombreInformalNormalizado>/<nombreNormalizado portfolio>/<nombreNormalizado colección>/<nombreFichero>` y se sirven en `/photos/...` con esa misma ruta, que coincide con la de la web. Los ids y el `usuario` son internos: no aparecen ni en la API ni en las URL. **En las URL y en las carpetas nunca hay mayúsculas, tildes ni espacios.** **`normalizarNombre()`** (`backend/src/utils/normalizar-nombre.ts`) es el único helper que normaliza nombres (fotógrafos, portfolios y colecciones): quita los espacios de los extremos, pasa a minúsculas, "ñ" -> "ny", quita tildes y cambia cada grupo de espacios intermedios por un guion (`/lucia-martin/proyectos-personales/editorial`, "Montaña" -> `montanya`, "Irene Castaño" -> `irene-castanyo`). Está duplicada a propósito en el frontend (`core/utils/normalizar-nombre.ts`, solo para el guard de URL canónica) y debe mantenerse idéntica. Un nombre cuya forma normalizada no sirve como carpeta (contiene `/` o `\`, o empieza por `.`) se rechaza con la regla `NOMBRE_NO_VALIDO`. El backend la registra como función SQL (`db.function` en `db/conexion.ts`, porque `lower()` de SQLite solo convierte ASCII) para normalizar el segmento que llega en la URL antes de compararlo con la columna normalizada, así que la API acepta cualquier variante. En la web, el guard `core/guards/url-canonica.ts` (en las rutas con parámetros) redirige cualquier URL escrita con mayúsculas, tildes o espacios a su forma canónica (`/Santi Estévez` -> `/santi-estevez`, `/marta-vidal/encargos/montaña` -> `.../montanya`). "Ciudad de noche", "Ciudad-de noche" o "ciudad de noche" darían la misma URL y la misma carpeta: las reglas de negocio lo rechazan y el índice único sobre `nombreNormalizado` es la última defensa. Tampoco se controlan las mayúsculas en `nombreFichero` (las URL de `/photos/` usan el nombre real del fichero). Si `normalizarNombre()` cambia, habría que recalcular las columnas normalizadas y renombrar las carpetas (con una migración). La API usa el mismo vocabulario que la BD (`nombre`, `descripcion`, `fotos`, `nombreFichero`, `titulo`, `orden`, `ancho`, `alto`…); solo los campos calculados siguen en inglés (`coverPhotoUrl`, `photoCount`, `collectionCount`, `portfolioCount`, `logoUrl`, `url`).

- Fuente de verdad: la base de datos SQLite `backend/datos/BD/portfolio.db` (ruta configurable con `DB_PATH`; no versionada: `backend/datos/` está en `.gitignore`). Esquema en `backend/src/db/conexion.ts`, notación lowerCamelCase: `usuarios` (PK `idUsuario`, `usuario` único, `email` opcional y único sin distinguir mayúsculas, `passwordHash`, `rol` `'usuario'`/`'administrador'` con un único administrador, `fechaUltimoAcceso`, `temaPreferido` `'oscuro'`/`'claro'`/NULL, `fotoActualizada`: cuándo se puso su foto de perfil, NULL si no tiene), `sesiones` (hash del token, `fechaExpiracion`), `fotografos` (PK `idFotografo`, FK `idUsuario` obligatoria y única, en cascada: borrar el usuario borra su fotógrafo; `nombreInformal`, `nombreInformalNormalizado` único, `nombre`, `primerApellido`, `segundoApellido`, `descripcion`), `portfolios` (PK `idPortfolio`, FK `idFotografo`, `nombreNormalizado`, `nombre`, `descripcion`, `idColeccionPortada` FK a `colecciones` ON DELETE SET NULL, `visible` 0/1, `orden`; UNIQUE `(idFotografo, nombre)` e índice único `(idFotografo, nombreNormalizado)`), `colecciones` (PK `idColeccion`, FK `idPortfolio`, `nombreNormalizado`, `nombre`, `descripcion`, `idFotoPortada` FK a `fotos`, `visible` 0/1, `orden`; UNIQUE `(idPortfolio, nombre)` e índice único `(idPortfolio, nombreNormalizado)`), `fotos` (PK `idFoto`, FK `idColeccion`, `nombreFichero` único por colección, `titulo`, `orden`, `ancho`, `alto`) y `coleccionTags` (PK `idColeccion, tag`). Claves foráneas en cascada; los fotógrafos se listan por `idFotografo` (orden de alta). `usuarios`, `fotografos`, `portfolios`, `colecciones` y `fotos` tienen `fechaCreacion` y `fechaModificacion` (texto ISO 8601 UTC) mantenidas por la BD: DEFAULT y un trigger `<tabla>FechaModificacion` AFTER UPDATE. `passwordHash` guarda solo el hash scrypt (NULL si no tiene contraseña) y ni el email, ni el hash, ni el `usuario` salen nunca en la API pública (el email solo en `GET …/edicion`). La versión del esquema va en `PRAGMA user_version` (`VERSION_ESQUEMA`, hoy 17). Una BD nueva (versión 0) se crea con `ESQUEMA` y el administrador (`crearOAbrir()` en `db/conexion.ts`). **Migraciones** desde la versión 15: cada cambio de esquema sube la versión y añade en `MIGRACIONES` (`db/conexion.ts`) la de la anterior, que conserva los datos y se aplica en una transacción al abrir la BD (15 -> 16: `portfolios.idColeccionPortada`; 16 -> 17: `visible` en `portfolios` y `colecciones`); una BD de otra versión (anterior a la 15 o posterior) no se abre (el backend no arranca, para no perder datos). Al cambiar el esquema, actualizar a la vez `ESQUEMA` (BD nuevas) y `MIGRACIONES` (existentes). Cuidado al editar `conexion.ts` con `npm run dev` en marcha: el backend se recarga en cada guardado; pararlo antes de tocar el esquema. `organizacionFotos.json` ya no existe (estaba desfasado respecto a la BD y las carpetas): solo queda `npm run db:importar -- <fichero.json>` para cargas masivas puntuales (hoy, la única forma de dar de alta fotos en bloque). Ese JSON usa el mismo vocabulario: `OrganizacionFotos[]`, cada elemento `{ fotografo: { nombreInformal, usuario?, nombre, primerApellido, segundoApellido?, email?, descripcion }, portfolios: [{ nombre, descripcion?, colecciones: [{ nombre, descripcion?, tags, fotoPortada? (nombreFichero), fotos: [{ nombreFichero, titulo?, orden, ancho?, alto? }] }] }] }` (tipos en `backend/src/types/catalogo.ts`; `usuario` opcional para fijarlo si hay homónimos; la contraseña no se importa). Con `--reemplazar` borra antes todo el catálogo de la BD; con `--anyadir` lo añade al existente (pasando las mismas reglas, p. ej. un nombre informal repetido lo rechaza).
- Archivos de imagen reales: `backend/datos/fotos/<nombreInformalNormalizado>/<nombreNormalizado del portfolio>/<nombreNormalizado dla colección>/<nombreFichero>` — deben coincidir exactamente con lo guardado en la BD, o las imágenes no se resolverán. Al importar un JSON las carpetas ya deben llamarse así (la importación no las crea ni las renombra).
- Logos de fotógrafo: nunca los aporta el usuario ni se anotan en la BD; los genera el backend. `GET /api/fotografos/:fotografo/logo` llama a `asegurarLogo` (`backend/src/services/logo.service.ts`), que sirve `backend/datos/logos/<nombreInformalNormalizado>.svg` (p. ej. `lucia-martin.svg`, `irene-castanyo.svg`) y, si no existe, lo genera con el `nombreInformal` como firma. Al cambiar el `nombreInformal`, `cambiarNombreInformal()` borra el logo anterior y se genera uno nuevo en la siguiente petición. El logo es un SVG tipo firma en letra manuscrita Mrs Saint Delafield con un subrayado de plumilla, con el texto convertido a trazos (un `<img>` no puede cargar fuentes) y tinta `#f2f1ed` para el fondo oscuro. La fuente (OFL) está en `backend/assets/fonts` y se copia a la imagen Docker. La API expone solo `logoUrl`.
- Miniaturas: la web no muestra las fotos originales (de miles de píxeles y varios MB, que el navegador reduciría al vuelo con un filtro rápido, con dientes de sierra y grano) sino versiones reducidas que genera el backend con `sharp` (filtro Lanczos, orientación EXIF, perfil sRGB, JPEG calidad 85) a 480, 960, 1600 y 2400 px de ancho, sin ampliar nunca. Se piden como la foto más `?ancho=<ancho>` (`/photos/…/foto.jpg?ancho=960`; otro ancho: 400) y se generan la primera vez en `datos/miniaturas/<ancho>/<misma ruta>`, una caché interna como los logos (en Docker, en la carpeta de datos, `DATOS_PATH`): se regeneran si la original es más reciente y se pueden borrar sin perder nada. Lógica en `services/miniatura.service.ts` (con `sharp.cache(false)`, porque su caché deja los ficheros abiertos y en Windows impide renombrar o borrar después las fotos) y `routes/miniaturas.routes.ts` (middleware delante de `express.static` en `/photos`; si no se puede generar, sirve la original). Al eliminar o renombrar una foto, colección, portfolio o fotógrafo se borran sus miniaturas (`borrarMiniaturas()`). En la web, la directiva `shared/foto-reducida/` (`<img [appFotoReducida]="url" tamanyos="…">`) pone `src`, `srcset` con los cuatro anchos y `sizes`, y el navegador elige la versión más cercana al tamaño en pantalla; la usan todas las imágenes de fotos y portadas, también el visor. `/photos` no sirve nada con un segmento que empiece por punto (`dotfiles: 'ignore'`; por defecto `express.static` sí serviría los ficheros de dentro de una carpeta con punto, como las papeleras).
- Tipos compartidos conceptualmente (no compartidos por código, ya que son dos paquetes npm separados): `backend/src/types/catalogo.ts` y `frontend/src/app/core/models/catalogo.model.ts`. Si se cambia la forma del JSON hay que actualizar ambos.

### Backend (`backend/src/`)

- `index.ts` — arranque de Express, monta `/api` y sirve `/photos` como estático desde `backend/datos/fotos`.
- `routes/catalogo.routes.ts` — único router: `GET /api/colecciones` (todas las colecciones con su `fotografo` (nombreInformal) y `portfolio`, filtro opcional `?tag=`), `GET /api/tags` (tags únicos derivados de todas las colecciones), `GET /api/fotografos` (con `portfolioCount` y `collectionCount`), `POST /api/fotografos` (alta: `crearFotografo()` en `services/fotografo.service.ts`; cuerpo `FotografoAlta` con `nombreInformal`, `nombre`, `primerApellido` obligatorios y `segundoApellido`, `email`, `descripcion`, `contrasenya` opcionales; responde 201 con los datos públicos, 400 si el cuerpo está mal formado y 422 si incumple una regla; crea también la carpeta `datos/fotos/<nombreInformalNormalizado>` en la misma transacción y guarda solo el hash scrypt de la contraseña, `utils/contrasenya.ts`), `GET /api/fotografos/:fotografo` (fotógrafo + resúmenes de sus portfolios), `GET /api/fotografos/:fotografo/edicion` (datos editables para el formulario, incluido el email; de la contraseña solo `tieneContrasenya`), `PUT /api/fotografos/:fotografo` (edición: mismo cuerpo que el alta, una contraseña vacía conserva la actual; si cambia el nombre informal renombra la carpeta), `DELETE /api/fotografos/:fotografo` (elimina con su usuario, portfolios, colecciones, fotos, carpeta y logo; si tiene portfolios exige `?confirmar=true`, si no responde 422 con la regla `FOTOGRAFO_ELIMINAR_CON_PORTFOLIOS`, cuyo mensaje es la pregunta que muestra la web; 204 si se elimina), `GET /api/fotografos/:fotografo/logo`, `GET /api/fotografos/:fotografo/portfolios/:portfolio` (portfolio + resúmenes de sus colecciones, filtro opcional `?tag=`; también es lo que carga el formulario de edición), `POST /api/fotografos/:fotografo/portfolios` (alta: cuerpo `PortfolioAlta` `{ nombre, descripcion? }`; se añade al final de los del fotógrafo y crea su carpeta; 201 con el `PortfolioDetalle`, 400 si el cuerpo está mal formado, 422 si incumple una regla), `PUT /api/fotografos/:fotografo/portfolios/:portfolio` (mismo cuerpo; si cambia el nombre renombra la carpeta; devuelve el portfolio con su nuevo `nombreNormalizado`), `PUT /api/fotografos/:fotografo/orden-portfolios` (cuerpo `{ orden: [nombreNormalizado, …] }` con todos los portfolios del fotógrafo en su nuevo orden, 0, 1, 2…; 204; 422 `PORTFOLIO_ORDEN_NO_VALIDO` si no son exactamente sus portfolios, cada uno una vez; `ordenarPortfolios()` en `portfolio.service.ts`, operación `ORDENAR_PORTFOLIOS`), `DELETE /api/fotografos/:fotografo/portfolios/:portfolio` (elimina con colecciones, fotos y carpeta; si tiene colecciones exige `?confirmar=true`, si no 422 con la regla `PORTFOLIO_ELIMINAR_CON_COLECCIONES`; 204), `GET /api/fotografos/:fotografo/portfolios/:portfolio/colecciones/:coleccion` (colección con `portfolio: { nombre, nombreNormalizado }` y `fotos`; también es lo que carga el formulario de edición), `POST /api/fotografos/:fotografo/portfolios/:portfolio/colecciones` (alta: cuerpo `ColeccionAlta` `{ nombre, descripcion?, tags? }`; se añade al final de las del portfolio y crea su carpeta; 201 con el `ColeccionDetalle`, 400/422 como en portfolios), `PUT …/colecciones/:coleccion` (mismo cuerpo, sin tags = ninguno; si cambia el nombre renombra la carpeta), `PUT …/portfolios/:portfolio/portada` (cuerpo `{ coleccionPortada: nombreNormalizado | null }`: la colección cuya portada es la del portfolio, o ninguna, y entonces es la primera; 204; 422 `PORTFOLIO_COLECCION_PORTADA_INEXISTENTE` si no es una de sus colecciones; `cambiarPortadaPortfolio()` en `portfolio.service.ts`, operación `CAMBIAR_PORTADA_PORTFOLIO`; `GET …/portfolios/:portfolio` devuelve la elegida en `coleccionPortada`; al importar JSON, `coleccionPortada` opcional del portfolio, con el nombre de la colección), `PUT …/portfolios/:portfolio/orden-colecciones` (cuerpo `{ orden: [nombreNormalizado, …] }` con todas las colecciones del portfolio en su nuevo orden, que se guarda como 0, 1, 2…; 204; 422 `COLECCION_ORDEN_NO_VALIDO` si no son exactamente sus colecciones, cada una una vez; no cuelga de `/colecciones` para no confundirse con una colección llamada "orden"; `ordenarColecciones()` en `coleccion.service.ts`, operación `ORDENAR_COLECCIONES`) y `DELETE …/colecciones/:coleccion` (elimina con fotos y carpeta; si tiene fotos exige `?confirmar=true`, si no 422 con la regla `COLECCION_ELIMINAR_CON_FOTOS`; 204), `POST …/colecciones/:coleccion/fotos?nombreFichero=<nombre>` (una foto por petición: el cuerpo es la imagen tal cual, `Content-Type: image/*`; se reconoce por su contenido JPEG/PNG/WebP y se leen ancho y alto de su cabecera, `utils/imagen.ts`; máximo 25 MB; se añade al final de las de la colección con su nombre original; 201 con la foto; 422 `FOTO_NOMBRE_FICHERO_NO_VALIDO`, `FOTO_FICHERO_DUPLICADO` —también si el fichero ya está en la carpeta— o `FOTO_FORMATO_NO_VALIDO`), `PUT …/colecciones/:coleccion/fotos/orden` (cuerpo `{ orden: [nombreFichero, …] }` con todas las fotos de la colección en su nuevo orden, que se guarda como 0, 1, 2…; 204; 422 `FOTO_ORDEN_NO_VALIDO` si no son exactamente sus fotos, cada una una vez), `PUT …/colecciones/:coleccion/portada` (cuerpo `{ fotoPortada: nombreFichero | null }`: elige la foto de portada —`colecciones.idFotoPortada`— o ninguna, y entonces la portada es la primera foto; 204; 422 `COLECCION_FOTO_PORTADA_INEXISTENTE` si no es una de sus fotos; `cambiarPortada()` en `coleccion.service.ts`, operación `CAMBIAR_PORTADA_COLECCION`; `GET …/colecciones/:coleccion` devuelve la elegida en `fotoPortada`) `PUT …/colecciones/:coleccion/fotos/:nombreFichero/titulo` (cuerpo `{ titulo: texto | null }`; se guarda sin espacios en los extremos y vacío o "Sin título" es NULL, sin título; menos de 20 caracteres, regla `FOTO_TITULO_DEMASIADO_LARGO`, que también valida la importación; responde con la foto; `cambiarTituloFoto()` en `foto.service.ts`, operación `CAMBIAR_TITULO_FOTO`) y `DELETE …/colecciones/:coleccion/fotos/:nombreFichero` (registro y fichero; si era la portada, pasa a serlo la primera; 204); lógica en `services/foto.service.ts` (BD y fichero en la misma transacción; el nombre del fichero va codificado en las URL de `/photos/`); `frontend/nginx.conf` admite cuerpos de hasta 30 MB en `/api/`; `:fotografo`, `:portfolio` y `:coleccion` son segmentos de URL (ver `normalizarNombre`). Portfolios y colecciones salen siempre con su `nombreNormalizado`, que la web usa para los enlaces. Los datos públicos del fotógrafo son `nombreInformal`, `nombre`, `primerApellido`, `segundoApellido?`, `descripcion` y `logoUrl`.
- `config/rutas.ts` — rutas a `datos/` (configurable con `DATOS_DIR`, p. ej. para tests), fotos (`datos/fotos` o `FOTOS_DIR`, que usa Docker), logos y base de datos (`DB_PATH`, por defecto `datos/BD/portfolio.db`). `db/conexion.ts` — abre la BD (WAL, `foreign_keys`) y crea el esquema. `db/importar.ts` — importa un catálogo en JSON en una transacción (lo usan `db:importar` y los tests para preparar datos). `db/catalogo.repository.ts` — todas las consultas (sentencias preparadas); abre la BD al cargarse. `scripts/importar-json.ts` — CLI de importación (`npm run db:importar -- <fichero.json>`; en el contenedor `node dist/scripts/importar-json.js <fichero.json>`). `services/logo.service.ts` — generación y persistencia de logos. `utils/normalizar-nombre.ts` — `normalizarNombre()` y `esNombreNormalizadoValido()`. `utils/carpetas.ts` — `carpetaOcupada()` (sin confundir un cambio solo de mayúsculas con otra carpeta) y `renombrarCarpeta()`. El paquete es ESM (`"type": "module"`, `module`/`moduleResolution: NodeNext`).
- `reglas/` — **reglas de negocio** (ver sección "Reglas de negocio"). `errores.ts` — `RecursoNoEncontrado` (404). `gestionar-errores.ts` — middleware de Express que responde 422 a una regla incumplida y 404 a un recurso inexistente. `services/fotografo.service.ts` — `crearFotografo`, `editarFotografo`, `cambiarNombreInformal` y `eliminarFotografo`: validan las reglas en su operación y mantienen la carpeta del fotógrafo sincronizada con la BD (al eliminar, la carpeta se aparta a `datos/fotos/.papelera-*` dentro de la transacción y se borra después; las carpetas con punto no se sirven en `/photos`). `services/portfolio.service.ts` — `crearPortfolio`, `editarPortfolio`, `eliminarPortfolio` y `renombrarPortfolio`, con el mismo esquema (validar en su operación, BD y carpeta en la misma transacción). `services/coleccion.service.ts` — `crearColeccion`, `editarColeccion` (nombre, descripción y tags), `eliminarColeccion` y `renombrarColeccion`, igual. Al eliminar (fotógrafo, portfolio o colección) la carpeta se aparta con `apartarCarpeta()` y se borra con `vaciarPapelera()` (`utils/carpetas.ts`). **El mantenimiento de portfolios y colecciones es cosa del fotógrafo propietario, no del administrador**: sus rutas cuelgan del fotógrafo (API) y de `/gestion/:fotografo/…` (web), para que, cuando haya login, baste con comprobar que el usuario es ese fotógrafo.

### Reglas de negocio (`backend/src/reglas/`)

Todo lo que la aplicación no permite ("un fotógrafo no puede tener dos portfolios con el mismo nombre") se gestiona en un único módulo:

- `catalogo.ts` — **único sitio donde se definen las reglas y se redactan sus textos**: `REGLAS` (código -> mensaje, p. ej. `PORTFOLIO_NOMBRE_DUPLICADO: 'Ya existe otro portfolio con el mismo nombre ("{nombre}") para este fotógrafo.'`) y `OPERACIONES` (código -> descripción en infinitivo de lo que se intentaba hacer, p. ej. `CREAR_PORTFOLIO: 'Crear el portfolio "{nombre}" del fotógrafo "{fotografo}"'`). Los `{campo}` se rellenan con los datos al incumplirse.
- `regla-incumplida.ts` — el error `ReglaNegocioIncumplida` (código, datos, mensaje de la regla y, opcionalmente, la operación intentada), `exigir(condición, código, datos)` / `incumplir(código, datos)` para lanzarlo, y `enOperacion(códigoOperación, datos, fn)` que envuelve una acción para que cualquier regla incumplida dentro salga acompañada de lo que se intentaba (se conserva la operación más interna). `toJSON()` es la respuesta de la API y `aTexto()` la salida de consola.
- `validaciones.ts` — `validadorCatalogo(db)`: las comprobaciones que consultan la BD (nombres de portfolio/colección duplicados comparados en su forma normalizada, nombres que no sirven como carpeta, carpeta de destino ocupada al renombrar, nombre informal repetido, y en `usuario()` las de la cuenta —correo con formato válido y no repetido, nombre de usuario no repetido, longitud mínima de la contraseña: reglas `USUARIO_*`—, fichero repetido en una colección, foto de portada inexistente, tags repetidos, obligatorios…). Aceptan el id del propio elemento (`excluir`) para las modificaciones. El repositorio exporta `validar` (validador sobre la conexión principal).

Todo lo que escribe en el catálogo debe validar antes de guardar y envolverse en su operación: la importación (`db/importar.ts`: `CREAR_FOTOGRAFO`, `CREAR_PORTFOLIO`, `CREAR_COLECCION`, `ANYADIR_FOTO`) `cambiarNombreInformal()` (`CAMBIAR_NOMBRE_INFORMAL`) y `renombrarPortfolio()` / `renombrarColeccion()` (`RENOMBRAR_PORTFOLIO`, `RENOMBRAR_COLECCION`), `crearPortfolio()` / `editarPortfolio()` / `ordenarPortfolios()` / `eliminarPortfolio()` (`CREAR_PORTFOLIO`, `EDITAR_PORTFOLIO`, `ORDENAR_PORTFOLIOS`, `ELIMINAR_PORTFOLIO`), `crearColeccion()` / `editarColeccion()` / `ordenarColecciones()` / `eliminarColeccion()` (`CREAR_COLECCION`, `EDITAR_COLECCION`, `ORDENAR_COLECCIONES`, `ELIMINAR_COLECCION`), `anyadirFoto()` / `ordenarFotos()` / `eliminarFoto()` (`ANYADIR_FOTO`, `ORDENAR_FOTOS`, `ELIMINAR_FOTO`); cualquier endpoint de escritura futuro, igual. Las restricciones UNIQUE/NOT NULL de la BD se mantienen como última defensa. Para añadir una regla: código y mensaje en `catalogo.ts`, comprobación en `validaciones.ts` (o `exigir` donde toque) y un test en `reglas/reglas.test.ts`.

Una regla incumplida en la API se responde con **422** y este cuerpo: `{ tipo: "reglaNegocioIncumplida", operacion: { codigo, descripcion }, regla: { codigo, mensaje }, message }` (`message` = "No se ha podido <operación>. <regla>"). En los comandos (`db:importar`, `fotografo:renombrar`, `portfolio:renombrar`, `coleccion:renombrar`) se muestra la operación y la regla en consola y no se guarda nada (transacción).

### Frontend (`frontend/src/app/`)

Angular standalone (sin `NgModule`), routing con `loadComponent` (lazy):

- `core/services/catalogo.ts` — `CatalogoService` (decorador `@Service()`, la forma moderna de `@Injectable` en esta versión de Angular) con un método por ruta del backend (`getFotografos`, `getFotografo`, `getPortfolio`, `getColeccionDePortfolio`, además de los globales `getColecciones` y `getTags`).
- `core/models/catalogo.model.ts` — interfaces con los mismos nombres que la API (`Fotografo*`, `Portfolio*`, `ColeccionResumen`, `ColeccionEnCatalogo`, `ColeccionDetalle`, `Foto`) y la función `nombreCompleto()`.
- `core/config/api.config.ts` — URL base de la API.
- `features/fotografo-list/` — página raíz (`/`), listado de fotógrafos (solo el título y las tarjetas). El alta de fotógrafos desde el administrador (`/admin/fotografos/nuevo`) y el cambio de contraseña del administrador (`/admin/contrasenya`) no tienen enlace en la interfaz: se llega por su dirección. Los fotógrafos se dan de alta registrándose.
- `shared/usuario-sesion/` — derecha de la franja superior (`app.html`). Con sesión: círculo con las iniciales (aún no hay foto de perfil), el nombre informal (o "Administrador") y ▾; al pulsar, un menú desplegable con el círculo, el nombre y el correo, y las opciones "Mi perfil" (`/perfil`), "Configuración" (`/configuracion`) y "Salir" (cierra la sesión y vuelve a la portada); se cierra al pulsar fuera, con Escape o al elegir. Sin sesión: "Iniciar sesión", que abre `shared/panel-sesion/` (diálogo con usuario o correo y contraseña, y "¿No tienes cuenta? Regístrate"). `core/services/sesion.ts` (`SesionService`, signal `usuario`) consulta la sesión al arrancar (`comprobar()`, compartida) y aplica el tema preferido del usuario.
- **Foto de perfil**: sección "Foto de perfil" del formulario del fotógrafo (alta, edición y registro) con `shared/editor-foto/` (diálogo): origen un archivo o la cámara (`getUserMedia`, vista en espejo y "Capturar"; exige contexto seguro: https o localhost), y encuadre bajo una máscara circular que se mueve arrastrando (puntero o flechas) y se amplía con el deslizador, la rueda o +/- (hasta ×4), sin dejar nunca hueco en el círculo; "Aceptar" recorta en el navegador a un JPEG cuadrado de 512 px. Al editar se sube en el momento; en el alta y el registro, al crear el fotógrafo. Backend (`services/foto-perfil.service.ts`): `PUT /api/fotografos/:fotografo/foto` (cuerpo `image/jpeg`, máximo 2 MB; 422 `USUARIO_FOTO_NO_VALIDA`; devuelve `fotoUrl`), `DELETE …/foto` y `GET …/foto` (404 si no tiene; caché larga, porque la URL lleva `?v=<fotoActualizada>`). Se guarda en `datos/avatares/u<idUsuario>.jpg` (interno, como los logos; se borra al eliminar al fotógrafo) y sale como `fotoUrl` en la sesión, "Mi perfil" y `/edicion`. `shared/avatar/` muestra la foto o, si no hay, las iniciales (menú del usuario, "Mi perfil", formulario).
- `features/perfil/` — "Mi perfil" (`/perfil`): sus datos como usuario (cuenta) y, si lo es, como fotógrafo (con su firma y totales), con enlaces a su página, a editar sus datos y a la configuración. `features/configuracion/` — "Configuración" (`/configuracion`): de momento, el tema por defecto (claro u oscuro), que se guarda en su usuario y se aplica al iniciar sesión en cualquier navegador. Las dos exigen sesión (guard `core/guards/con-sesion.ts`; sin ella, a la portada).
- Registro: `/registro` reutiliza `features/fotografo-form/` con `data.modo = 'registro'`: añade "Datos de acceso" (usuario, y correo y contraseña obligatorios) sobre los datos de fotógrafo; al terminar la sesión queda iniciada y lleva a su página. `registro` es un segmento reservado (como `admin`, `api`, `configuracion`, `gestion`, `perfil` y `photos`).
- `features/primer-uso/` — bienvenida del primer uso (`/admin/primer-uso`): credenciales del administrador y, opcionalmente, contraseña nueva. `core/guards/primer-uso.ts` (`primerUsoPendiente`, `canActivateChild` de la ruta padre de todas las demás) lleva ahí mientras el primer uso esté pendiente; `core/services/administracion.ts` (`AdministracionService`) consulta `/api/estado` una sola vez y lo recuerda.
- `features/admin-contrasenya/` — cambio de la contraseña del administrador (`/admin/contrasenya`).
- `features/fotografo-form/` — páginas `/admin/fotografos/nuevo` (enlace "+ Nuevo fotógrafo" en la portada) y `/admin/fotografos/:fotografo/editar` (carga los datos de `/edicion`; contraseña vacía = conservar): formulario reactivo de alta y edición con los campos editables del fotógrafo (nombre informal, nombre, apellidos, correo, descripción, contraseña y su repetición). Valida lo básico en el navegador y muestra el aviso de la regla incumplida (operación intentada + motivo) si el backend responde 422; si va bien navega a la página del nuevo fotógrafo. `nombreInformalNormalizado` y `usuario` no se muestran. La ruta va antes que las de parámetros y el prefijo `admin` (igual que `api`, `gestion` y `photos`) está reservado: ningún fotógrafo puede tener esa dirección (regla `FOTOGRAFO_NOMBRE_INFORMAL_RESERVADO`).
- `features/portfolio-form/` — páginas `/gestion/:fotografo/portfolios/nuevo` (enlace "+ Nuevo portfolio" en la página del fotógrafo) y `/gestion/:fotografo/portfolios/:portfolio/editar`: formulario de nombre y descripción del portfolio, con el mismo aviso de regla incumplida que el del fotógrafo; si va bien navega a la página del portfolio. `gestion` es la zona del fotógrafo propietario (frente a `admin`, la del administrador).
- `features/coleccion-form/` — páginas `/gestion/:fotografo/portfolios/:portfolio/colecciones/nuevo` (enlace "+ Nueva colección" en la página del portfolio) y `.../colecciones/:coleccion/editar`: formulario de nombre, descripción y tags (separados por comas) dla colección, igual que el del portfolio; si va bien navega a la página dla colección.
- `features/coleccion-fotos/` — "Gestionar fotos" (`/gestion/:fotografo/portfolios/:portfolio/colecciones/:coleccion/fotos`, botón en la franja de la página de la colección): zona para arrastrar fotos o elegirlas en el equipo (varias a la vez), que se suben de una en una en ese orden (`CatalogoService.anyadirFoto`), con la lista de las que están en cola o no se han podido añadir (y el motivo, la regla incumplida); y cuadrícula de las fotos de la colección, numeradas y sin su nombre de fichero, con un cuadro de texto bajo cada foto para su título (vacío muestra "Sin título"; máximo 19 caracteres; se guarda al salir del cuadro o con Intro, Escape lo deshace, `cambiarTituloFoto`; mientras se escribe no se arrastran las tarjetas) y debajo una estrella a la izquierda (portada: solo el contorno si no lo es, rellena si lo es; pulsarla la elige o, si ya lo es, la quita, `cambiarPortada`) y "Eliminar" a la derecha (confirmación con `shared/confirmacion/`). Se ordenan arrastrando cada foto dentro de la cuadrícula: el resultado se ve mientras se arrastra, al soltar se guarda (`ordenarFotos`) y, si falla o se cancela con Escape, vuelve al orden anterior. No se puede reordenar mientras se sube o se elimina una foto.
- `features/coleccion-gestion/` — "Gestionar colecciones" de un portfolio (`/gestion/:fotografo/portfolios/:portfolio/colecciones/gestionar`, botón junto a "+ Nueva colección" en la página del portfolio): las colecciones en una cuadrícula (portada o "Sin fotos", nombre, número de fotos y posición) que se ordenan arrastrándolas, igual que las fotos (`ordenarColecciones`), y con una estrella junto al nombre para elegir la colección que da su portada al portfolio (rellena si lo es; pulsarla la elige o la quita, `cambiarPortadaPortfolio`; sin elegir, la primera) y, a la derecha, el ojo de la visibilidad (`cambiarVisibilidadColeccion`).
- `features/portfolio-orden/` — "Gestionar portfolios" de un fotógrafo (`/gestion/:fotografo/portfolios/ordenar`, botón junto a "+ Nuevo portfolio" en la página del fotógrafo): igual que la ordenación de "Gestionar colecciones", con sus portfolios (`ordenarPortfolios`), y con el ojo de la visibilidad de cada uno (`cambiarVisibilidadPortfolio`).
- `shared/visibilidad/` — `ojo-visibilidad` (botón de las páginas de gestión: un ojo si lo ve cualquiera, un ojo tachado y apagado si está oculto a los demás usuarios; pulsarlo lo cambia) y `marca-oculto` (el ojo tachado con "Oculto"/"Oculta", que en las páginas del catálogo señala lo oculto a quien puede verlo: en la esquina de la portada de las tarjetas y en la etiqueta de la cabecera). Las dos páginas comparten los estilos de `shared/estilos/_ordenar.scss`; cada una fija la proporción de la portada.
- `shared/aviso-visible/` — directiva `appAvisoVisible`: al aparecer el aviso de error de un formulario (`<div class="aviso" role="alert">`, arriba del todo) lo desplaza hasta el centro de la pantalla, para que se vea aunque se haya pulsado el botón del final. La llevan los avisos de los formularios de fotógrafo (alta, edición y registro), portfolio, colección, primer uso y contraseña del administrador; funciona porque los formularios ponen el aviso a `null` antes de cada envío.
- `shared/orden-arrastre/` — `OrdenPorArrastre<T>`: la lógica de ordenar una lista arrastrando sus elementos (drag & drop nativo del navegador, sin librerías; no funciona en pantallas táctiles), compartida por "Gestionar fotos", "Gestionar portfolios" y "Gestionar colecciones".
- `shared/coleccion-acciones/` — botones "Editar" y "Eliminar" de una colección, en cada tarjeta de la página del portfolio y en la cabecera de la página dla colección. Igual que `portfolio-acciones`, con la regla `COLECCION_ELIMINAR_CON_FOTOS`. Emite `eliminado` (la página del portfolio recarga; la dla colección vuelve al portfolio).
- `shared/portfolio-acciones/` — botones "Editar" y "Eliminar" de un portfolio, en cada tarjeta de la página del fotógrafo y en la cabecera de la página del portfolio. Igual que `fotografo-acciones`: si el portfolio tiene colecciones el backend responde con la regla `PORTFOLIO_ELIMINAR_CON_COLECCIONES` y su mensaje se muestra en `shared/confirmacion/`; al aceptar se repite con `?confirmar=true`. Emite `eliminado` (la página del fotógrafo recarga; la del portfolio vuelve al fotógrafo).
- `shared/fotografo-acciones/` — botones "Editar" y "Eliminar" de un fotógrafo, en cada tarjeta de la portada y en la cabecera de su página. Eliminar pide al backend borrar sin confirmar: sin portfolios se elimina sin más; con portfolios el backend responde con la regla `FOTOGRAFO_ELIMINAR_CON_PORTFOLIOS` y su mensaje se muestra en `shared/confirmacion/` (diálogo modal con "Sí, eliminar" / "Cancelar"); al aceptar se repite con `?confirmar=true`. Emite `eliminado` (la portada recarga la lista; la página del fotógrafo vuelve a la portada).
- `features/portfolio-list/` — página `/:fotografo` (segmento del `nombreInformal`), grid de portfolios del fotógrafo; muestra "Volver" solo si se ha llegado desde la portada.
- `features/coleccion-list/` — página `/:fotografo/:portfolio`, grid de colecciones del portfolio, con enlace de vuelta a los portfolios.
- `features/coleccion-detail/` — página `/:fotografo/:portfolio/:coleccion`, grid de fotos dla colección con enlace de vuelta a su portfolio (muestra "Colección no encontrada" si no existe); obtiene los parámetros vía `ActivatedRoute.paramMap` con `switchMap` + `toSignal`.
- `shared/lightbox/` — visor modal reutilizable (controlado por el padre vía `photos`/`index` como inputs y eventos `closeRequested`/`indexChange`); navegación por teclado (flechas, Escape).

Patrón de datos: los componentes usan `toSignal()` (`@angular/core/rxjs-interop`) sobre los observables de `CatalogoService` en lugar de `subscribe()` manual; no hay gestión de estado global (no hace falta con esta escala de app).

### Diseño / estilo

Sistema de diseño propio en SCSS (sin Angular Material ni Tailwind, por decisión explícita): tokens como custom properties en `frontend/src/styles.scss`. **Dos temas**: el oscuro (predeterminado) en `:root` y el claro en `:root[data-tema='claro']`, que redefine los mismos tokens; se elige en la franja superior (`shared/selector-tema/`, `core/services/tema.ts`, guardado en `localStorage` y aplicado ya en `index.html` para que no parpadee). Los componentes usan siempre tokens, nunca colores fijos (`--color-peligro*` para eliminar y errores, `--color-velo` para el fondo de los diálogos, `--filtro-logo`, que invierte en el tema claro los logos, generados con tinta clara); el visor de fotos (`shared/lightbox/`) también sigue el tema, con su propio fondo casi opaco (`--color-visor-fondo`). Tema oscuro: paleta neutra para que las fotos destaquen; tipografía serif `Cormorant Garamond` para títulos + `Inter` para UI, cargadas vía Google Fonts en `index.html`). Los estilos de cada componente son locales a su carpeta (`*.scss` junto al componente); el presupuesto de `angular.json` avisa si los de un componente pasan de 6 kB (error a partir de 8 kB). La cabecera a todo el ancho de las páginas de fotógrafo, portfolio y colección (datos a la izquierda —etiqueta con el tipo y el número de elementos, nombre y descripción—, mantenimiento a la derecha y línea separadora difuminada debajo, y bajo ella la franja `cabecera-barra` con "Gestionar portfolios" y "+ Nuevo portfolio", "Gestionar colecciones" y "+ Nueva colección", o "Gestionar fotos") está en el parcial `shared/estilos/_cabecera.scss`, que cada página incluye con `@use`. Los estilos comunes de los formularios están igual en `shared/estilos/_formulario.scss`.

### Despliegue con Docker (NAS)

`docker-compose.yml` en la raíz levanta dos servicios en la red interna `portfolio`, usando imágenes ya construidas en vez de build local:

- `backend` — imagen `ghcr.io/sestevez5/portoliosfotograficos-backend:latest`. No publica puerto al host; solo es accesible desde `frontend` a través de la red de Docker Compose.
- `frontend` — imagen `ghcr.io/sestevez5/portoliosfotograficos-frontend:latest`. Publica un único puerto al host (`FRONTEND_PORT`, por defecto 8080).

Las imágenes se construyen y publican automáticamente en GitHub Container Registry (GHCR) mediante `.github/workflows/docker-publish.yml` en cada push a `main` (tags `:latest` y `:<sha>`). Por eso el NAS **no necesita el código fuente**: solo `docker-compose.yml`, `.env` y las carpetas de fotos y datos (ver más abajo). Si el paquete de GHCR está en privado, hay que hacer `docker login ghcr.io` una vez en el NAS con un token con permiso `read:packages` antes de poder hacer `pull` (o marcar el paquete como público desde la configuración de GitHub).

`docker-compose.override.yml` (no se copia al NAS) añade `build: context: ...` a ambos servicios y Docker Compose lo aplica automáticamente cuando está presente junto a `docker-compose.yml` — así en local, con el repo completo, `docker compose build`/`up` siguen construyendo las imágenes desde los Dockerfiles en vez de tirar de GHCR. Los Dockerfiles (`backend/Dockerfile`, `frontend/Dockerfile`) son multi-stage: el backend hace `npm run build` + `npm ci --omit=dev` + `node dist/index.js`; el frontend hace `ng build` y sirve `dist/frontend/browser` con nginx.

`frontend/nginx.conf` hace de proxy inverso: sirve los estáticos de Angular y reenvía `/api/` y `/photos/` al servicio `backend:3000`, de forma que el navegador solo ve un origen. Por eso en build de producción `API_BASE_URL` debe ser `''` (ruta relativa) en vez de `http://localhost:3000`: `angular.json` usa `fileReplacements` en la configuración `production` para sustituir `api.config.ts` por `api.config.prod.ts` automáticamente en cualquier `ng build` (o `npm run build`) sin flags adicionales. En desarrollo (`ng serve`) se sigue usando `api.config.ts` tal cual.

**Desde el NAS se montan dos carpetas, hermanas**: la de fotos (bind mount de `FOTOS_PATH` en `/app/fotos`, que el backend usa por `FOTOS_DIR`, fijada en el Dockerfile) y la de datos de la aplicación (`DATOS_PATH` en `/app/datos`: base de datos `BD/portfolio.db`, `logos/`, `miniaturas/` y `avatares/`). Las dos deben ser escribibles por el contenedor. Están juntas para que una instantánea o copia de la carpeta del proyecto guarde a la vez la BD y las fotos, que deben corresponderse; la de datos no va dentro de la de fotos, y es interna (no se toca a mano con la aplicación en marcha: con WAL, `portfolio.db` sola puede estar incompleta). **Si `DATOS_PATH` no está definida**, `/app/datos` va en el volumen con nombre `datos-internos`, gestionado por Docker y no visible en el host (lo que se usaba hasta la 2.1; sobrevive a `pull`/`up -d`, se pierde con `docker compose down -v` o borrando el volumen); se mantiene por compatibilidad y para la preproducción en Windows. Pasar de una a otra: `docker compose stop backend`, `docker compose cp backend:/app/datos/. <DATOS_PATH>/`, definir `DATOS_PATH` en `.env` y `docker compose up -d`. En el primer arranque la BD se crea vacía (el backend crea las subcarpetas). Nada de `backend/datos` se hornea en la imagen (`backend/.dockerignore` la excluye) ni se versiona. Cargar una BD existente: con el backend parado, copiar `portfolio.db` a `<DATOS_PATH>/BD/` (o, con el volumen, `docker compose cp portfolio.db backend:/app/datos/BD/portfolio.db`), sin `-wal`/`-shm` y consolidando antes el WAL. Los logos y las miniaturas no hace falta copiarlos: se regeneran al pedirlos. `better-sqlite3` es un módulo nativo: el Dockerfile instala sus dependencias en una etapa `deps` con `python3 make g++` por si hay que compilarlo (p. ej. NAS ARM) y copia solo `node_modules` a la imagen final. Las rutas en el host del NAS se configuran con las variables `FOTOS_PATH` (obligatoria) y `DATOS_PATH` en un fichero `.env` (no versionado; ver `.env.example`) junto con `FRONTEND_PORT`.

Despliegue típico en el NAS (solo con `docker-compose.yml`, `.env` y las carpetas de fotos y datos, sin el resto del repo): `cp .env.example .env` (ajustar rutas), `docker compose pull`, `docker compose up -d`. Para desplegar una versión nueva más adelante: `docker compose pull && docker compose up -d` de nuevo.

## Versionado

Versionado semántico `MAYOR.MENOR.PARCHE` (semver), una única versión para todo el monorepo:

- **MAYOR**: cambios incompatibles (p. ej. cambios en la organización de `datos/` que obligan a migrar los datos del NAS, o rutas de la API que desaparecen).
- **MENOR**: funcionalidad nueva compatible hacia atrás.
- **PARCHE**: correcciones sin cambios de funcionalidad.

Al publicar una versión: actualizar `version` en `backend/package.json` y `frontend/package.json` (`npm version X.Y.Z --no-git-tag-version` en cada paquete, que también actualiza el lockfile), añadir la entrada en `CHANGELOG.md`, hacer commit en `develop`, fusionar en `main` y crear el tag anotado `vX.Y.Z` en `main`. El desarrollo diario va en `develop`; `main` solo recibe versiones.

## Notas para seguir desarrollando

- Guía para colaboradores (preparar el entorno, preproducción con Docker con su propia BD y carpeta de fotos, flujo de git): `CONTRIBUTING.md`. Mantenerla al día si cambian comandos, variables o el despliegue.
- Las fotos actuales son contenido de prueba generado como placeholders de color — hay que sustituirlas por fotos reales.
- **Desde que existe el alta de fotógrafos, la BD es la única fuente de verdad**: y no está en el repositorio. `db:importar -- <fichero> --reemplazar` borraría el catálogo existente. Hacer copias de `portfolio.db` antes de esas operaciones.
- **Las escrituras están protegidas por permisos** (ver "Permisos" en el modelo de datos): sin sesión no se puede modificar nada y cada usuario solo lo suyo. Pendiente antes de publicar fuera de la red local: servirla por **https** (la cookie de sesión lleva `Secure` solo si la petición llega por https, y la cámara de la foto de perfil lo exige) y restringir el CORS (hoy `origin: true`, pensado para desarrollo).
- Copias de seguridad: en local basta con copiar `portfolio.db` con el backend parado (con WAL activo existen también `portfolio.db-wal`/`-shm` mientras corre). En Docker con `DATOS_PATH`, una instantánea (Btrfs) de la carpeta del proyecto copia a la vez BD (con su `-wal`) y fotos de forma coherente; copiar ficheros sueltos con el backend en marcha no es seguro. Con o sin ella, copia en caliente de la BD con `docker compose exec backend node -e "require('better-sqlite3')('datos/BD/portfolio.db').backup('datos/BD/copia.db').then(() => console.log('ok'))"` y `docker compose cp backend:/app/datos/BD/copia.db .`. Las fotos se copian directamente desde su carpeta del NAS.
- `GET /api/colecciones` sin filtro devuelve todas las colecciones; con miles de colecciones (probado con 1.000 fotógrafos / 100.000 fotos: ~640 KB, ~40 ms) convendría paginarlo si se empieza a usar desde la interfaz. El resto de rutas responde en pocos ms a esa escala.
- Repositorio git inicializado, con remoto en GitHub (`https://github.com/sestevez5/portoliosfotograficos.git`, rama `main`).
